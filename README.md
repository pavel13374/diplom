# Sentinel — автоматизированное обнаружение угроз в процессе разработки

Стенд из двух половин, которые ничего не знают друг о друге напрямую и общаются
только через общий журнал событий:

- **Среда** (`:8787`) — живой отдел разработки в GitLab. Сотрудники пишут код,
  открывают merge request'ы, ревьюят друг друга, ходят в отпуска и дежурят.
  Иногда среди них действует злоумышленник.
- **Консоль защиты** (`:8788`) — рабочее место аналитика SOC. Читает тот же
  журнал, поднимает детекты, собирает их в инциденты, раскладывает по матрице
  MITRE ATT&CK и помогает довести расследование до отчёта.

Смысл работы — проверить, можно ли обнаружить вредоносную активность внутри
процесса разработки, **не имея разметки**: детектор видит ровно то же, что видел
бы настоящий SOC, — поток событий git и CI, без единой подсказки о том, где
атака.

---

## Быстрый старт (Windows)

```
START.bat
```

Поднимает обе консоли в отдельных окнах и открывает браузер.
`STOP.bat` — остановить. Пароль администратора берётся из переменной окружения
`SOC_ADMIN_PASS`; если она не задана, при старте генерируется случайный и
печатается в консоль.

Вручную:

```
python webapp.py        # среда, http://127.0.0.1:8787
python console.py       # защита, http://127.0.0.1:8788
```

Без доступа к GitLab стенд работает в автономном режиме: `SOC_OFFLINE=1`.
События при этом пишутся в журнал как обычно, наружу ничего не уходит.

Настройки живут в `web_config.json`. В репозитории его нет — он содержит токен
доступа к GitLab; рядом лежит `web_config.example.json` с той же структурой и
пустым токеном. Скопируйте его и впишите свой.

Проверить, что всё цело:

```
python run_tests.py
```

Четырнадцать наборов проверок:

| Набор | Что проверяет |
|---|---|
| compile | все модули компилируются |
| unit-detector | правила, оконные агрегаты, вероятностный UEBA, слияние рисков |
| selftest | сквозная работоспособность стенда |
| antileak | **в признаки детектора не просочились ПОЛЯ разметки симулятора** |
| leakage | **ни одно ЗНАЧЕНИЕ наблюдаемого признака не определяет метку** |
| stats | корректность статистического аппарата оценки |
| realmon | **секрет, внесённый руками, обнаружен по наблюдаемому и стал инцидентом** |
| llm-fallback | триаж работает и без запущенной модели |
| contrast | все пары «текст на фоне» держат WCAG 2.1 AA во всех трёх темах |
| page-scripts | **скрипты страниц разбираются и доходят до опроса данных** |
| a11y | клавиатура, роли, подписи, семантика таблиц; там же перевод RU/EN |

Отдельно — статическая проверка правил и замер их точности:

```
python tools/lint_rules.py     # правила не читают метку, техники в модели угроз
python tools/rule_quality.py   # точность каждого правила и вклад в шум
```

Проверки интерфейса (a11y, язык) требуют `node` и пакет `jsdom`:

```
npm install
```

Зависимость зафиксирована в `package.json`. Если jsdom не установлен, наборы
помечаются пропущенными, а не проваленными — прогон остаётся зелёным на машине
без фронтенд-инструментов. Но пропущенная проверка ничего не гарантирует,
поэтому перед защитой их стоит прогнать по-настоящему.

## Реальный мониторинг — «поймай меня сам»

Стенд не только проигрывает свои сценарии — он следит за **настоящим** GitLab.
Наблюдатель `tools/gitlab_watch.py` опрашивает Events API, берёт diff каждого
нового коммита, считает те же признаки содержимого (энтропия, secret-regex, имя
файла) и пишет `push`-событие в общий журнал — **без единой метки симулятора**.
Детектор на `:8788` разбирает его наравне с остальными.

```
watch_gitlab.bat        # или: python tools/gitlab_watch.py
```

Проверка вживую: при запущенном наблюдателе закоммитьте руками в свой GitLab
файл с секретом (например, `config/prod.env` со строкой вида
`GITLAB_TOKEN=glpat-…`). Через несколько секунд на консоли защиты появится
алерт по технике T1552 (Credential Access) и заведётся инцидент — система
поймала утечку по наблюдаемым признакам, а не по подсказке.

Ровно этот путь без сети проверяет набор `realmon`: он собирает событие точно
как наблюдатель, прогоняет через детектор и коррелятор и требует алерт +
инцидент, а чистый коммит без секретов оставляет без тревоги.

## Как это устроено

```
Среда (webapp.py)                  Журнал событий            Защита (console.py)
  агенты, планировщик   ──пишет──▶   event-store   ──читает──▶  детектор → корреляция
  GitLab REST API                    SQLite, WAL                правила + UEBA → инциденты
                                     курсор чтения              ATT&CK, LLM-триаж, отчёты
```

Ключевое ограничение, на котором держится вся честность эксперимента: **защита
никогда не видит меток симулятора**. Она получает только наблюдаемые поля —
кто, когда, в каком репозитории, что сделал. Метка «это была атака» живёт в
другом слое и используется исключительно постфактум, при подсчёте точности.

Одного вырезания полей разметки для этого мало. Раньше каждый шаг атаки эмитил
собственное «говорящее» действие — `steal_oauth`, `repo_enum`, `mass_delete`, —
которого у обычных сотрудников не бывает. Поля разметки при этом были честно
срезаны, но правило вида `{"action": "steal_oauth"}` не обнаруживало атаку, а
читало ответ под другим именем.

Поэтому введён **нормализованный словарь действий** (`taxonomy.py`): и обычная
работа, и атака описываются одними и теми же действиями, какие видны в аудит-логе
GitLab, а различаются только наблюдаемыми атрибутами. «Кража OAuth-токена» — это
теперь `api_read(api_path="/oauth/tokens")`, ровно то, что увидел бы настоящий
SOC. Отличить это от легитимного обращения можно только по частоте, времени и
связке с другими событиями — то есть детектор обязан детектировать.

Проверяется тестом `tests/test_leakage.py`: для каждого наблюдаемого признака
считается взаимная информация с меткой (с поправкой на кардинальность через
перестановки), и ни одно значение не должно встречаться только у атаки.

### Слои обнаружения

| Слой | Что ловит | Чем силён |
|---|---|---|
| Обогащение | скользящие агрегаты по актору: всплески удалений, интенсивность API-чтений, охват репозиториев | без него «массовость» и «разведка» неотличимы от единичного нормального действия |
| L0 Detection-as-Code | известные приёмы: секрет в коммите, merge без ревью, ослабление branch-protection | точность, объяснимость, готовый маппинг на ATT&CK |
| L1 UEBA | отклонения от привычного поведения: скор = неожиданность события **в битах** | порог выводится из данных под бюджет тревог, а не назначается константой |
| L2 ML | то, под что правило ещё не написано; обобщается на форматы секретов, которых не видел | линейная модель с калибровкой Платта — вклад каждого признака виден аналитику |
| Корреляция | склейка разрозненных детектов одного актора в инцидент с kill-chain | превращает шум в историю атаки |
| LLM-триаж | человеческий разбор инцидента и приоритет | снимает рутину с аналитика; при недоступности модели работает детерминированный разбор |

Слияние рисков — **сумма лог-шансов с затуханием**, а не noisy-OR: слои смотрят
на одно событие и не являются независимыми, а noisy-OR при зависимых источниках
систематически завышает риск.

Модель слоя L2 в репозитории не лежит — она воспроизводится:

```
python research/train_runtime_model.py    # -> models/runtime_model.json
```

Без файла модели слой L2 молча выключается, стенд работает на L0 + L1.

38 правил лежат в `detections/*.json` — обычные файлы, их можно править и
добавлять без перезапуска логики: правило описывается декларативно.

### Как читать метрики

Все доли приводятся с доверительными интервалами (Уилсон 95%), MTTD — с
bootstrap-интервалом. Точечная оценка без интервала создаёт ложную точность:
«recall 74.5%» на 55 эпизодах — это на самом деле «где-то между 61 и 85%».

Основная интегральная метрика — **PR-AUC**, а не ROC-AUC. При доле атакующих
событий порядка процента ROC-AUC выглядит прекрасно даже у слабого детектора,
потому что знаменатель FPR — огромное число нормальных событий. Базовый уровень
PR-AUC равен доле положительного класса, поэтому его и надо держать рядом с
цифрой.

Сравнения конфигураций детектора проверяются **тестом Макнемара** на парных
исходах по одним и тем же эпизодам, с поправкой Холма на множественные
сравнения (`research/experiments.py`). «Различие незначимо» — честный результат,
а не неудача.

### Как считается покрытие ATT&CK

Матрица в консоли — это **модель угроз контура разработки**: 46 техник MITRE
ATT&CK Enterprise, которые в принципе наблюдаемы по событиям git, CI/CD и
GitLab API. Правила закрывают 33 из них, то есть покрытие — около 72%,
а остальные 13 честно горят как слепые зоны и образуют очередь работ для
detection engineering.

Это сделано намеренно. Если положить в матрицу только те техники, под которые
правила уже написаны, покрытие всегда будет 100% — метрика начнёт измерять
сама себя и потеряет смысл. Техники, принципиально ненаблюдаемые в этом
контуре (фишинг, эндпоинт, сетевой уровень), в матрицу не включены: их
отсутствие — граница системы, а не пробел в правилах.

## Разделы консоли защиты

**Обзор** — состояние платформы, живая лента детектов, очередь инцидентов,
покрытие ATT&CK, качество детектирования по подтверждённым вердиктам.

**Алерты** — таблица потока: поиск, сортировка, фильтры, постраничный вывод,
карточка детекта сбоку.

**Инциденты** — рабочее место расследования: таймлайн, доказательства,
связанные детекты, разбор моделью, техники ATT&CK, действия и заметка аналитика.

**Дела** — несколько инцидентов объединяются в одно расследование:
ответственный, статус, приоритет, история действий, печатная сводка.

**Очередь триажа** — приоритет, SLA, вердикты TP/FP с клавиатуры.

**ATT&CK Coverage** — матрица покрытия с переходом из техники в инциденты и
выгрузкой слоя для ATT&CK Navigator.

**Детекты** — каталог правил: что сработало, что молчит, карточка правила.

**Сущности** — поведенческие профили: что для человека норма и насколько
сегодняшний день от неё отличается.

**Профиль риска** — рейтинг разработчиков и репозиториев по риску и динамика во
времени. Оценка складывается из пикового и среднего риска, объёма детектов,
разнообразия техник и числа инцидентов.

**Red Launcher** — запуск атакующих кампаний: от разведки до выгрузки.

**Реплей прогона** — весь прогон как запись: детекты, тактики и инциденты на
одной шкале с курсором и воспроизведением.

**Тренды** и **Диагностика** — метрики во времени и техническое состояние.

## Обратная связь аналитика

Вердикты TP/FP — не украшение. Они переживают перезапуск (идентификаторы
инцидентов детерминированы), из них считается живая точность детектирования, а
правило, трижды помеченное как ложное срабатывание, автоматически уходит в
приглушённые и перестаёт засорять очередь. Это видно на дашборде: сколько
инцидентов разобрано, какая точность, какие правила шумят.

При старте консоль переигрывает последние события из журнала и восстанавливает
картину — инциденты и вердикты не теряются между запусками.

tests/             юнит-тесты, самопроверка, анти-лик, контраст, доступность

## Интерфейс

Три темы: тёмная (по умолчанию, язык SIEM/XDR), светлая и яркая — переключаются
кнопкой в верхней панели, выбор запоминается. Рядом переключатель языка RU/EN:
переводится оболочка продукта, а имена разработчиков, названия репозиториев и
тексты из журнала остаются как есть — это данные, их не переводят. Есть
командная палитра по `Ctrl+K` и сворачиваемое меню.

Обе консоли собраны на одной дизайн-системе (`static/design-system.css`). Три
правила, которые в ней соблюдаются жёстко:

- цвет нигде не задаётся напрямую, только через семантические токены;
- капс — только в шапках таблиц, подписи набираются обычным регистром;
- любая пара «текст на фоне» держит WCAG 2.1 AA, и это считается тестом, а не
  проверяется на глаз.

Интерфейсом можно пользоваться без мыши: навигация получает фокус табом,
у иконок есть подписи для скринридера, уровень критичности различается не
только цветом, но и формой значка, а анимации отключаются при системной
настройке «меньше движения».

## Ограничения

Стенд синтетический: сотрудники, репозитории, секреты и атаки придуманы.
Секреты в коммитах — фальшивые строки, похожие по форме на настоящие токены.
Разрушающие операции над GitLab вынесены в отдельные скрипты и не запускаются
сами.
