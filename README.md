# SOC GitLab Simulator

Симулятор работы SOC-команды в GitLab. Имитирует живой отдел детект-инженеров:
правила, code review с настоящими approvals и CI-пайплайнами, тюнинг, откаты,
депрекейты, threat intel, инциденты, тикеты, спринты, релизы, стендапы и
сюжетные кампании реагирования — всё в **таймлапсе** по виртуальным часам
(можно прогнать «сутки работы отдела за час»).

## Быстрый старт (Windows)

**Вариант 1 — веб-админка (рекомендуется):** дважды кликни **`run.bat`**.
Он установит зависимости, откроет браузер на `http://127.0.0.1:8787` и запустит
панель управления. Логин/пароль по умолчанию: **`admin` / `123`**.

**Вариант 2 — консоль:** дважды кликни **`run_cli.bat`** (симуляция в окне терминала).

Вручную:
```bash
pip install -r requirements.txt
python webapp.py     # веб-админка
python main.py       # консольный режим
```

## 🖥 Веб-админка

`run.bat` → браузер → вход `admin / 123`. На одной странице:

  рабочие часы, масштаб таймлапса, off-hours режим, статус подключения к GitLab,
  что прямо сейчас делает команда, uptime.
- **Сводка:** спринт, число правил, итерации, успехи/ошибки, пропуски off-hours.
- **Команда — кто на смене:** список агентов; зелёная точка — на рабочем дне,
  жёлтая — PTO; бейджи on-call / PTO.
- **Активности:** счётчики по каждому типу сценария.
- **Живые логи:** весь поток действий симулятора в реальном времени.
- **▶ Запустить / ⏹ Остановить** и **сброс состояния**.
- **⚙ Параметры:** редактор всех ключевых настроек (таймлапс, рабочие часы,
  off-hours, темп, фичи, GitLab) — применяются на лету и сохраняются в
  `web_config.json` (переживают перезапуск).

Логин/пароль и порт меняются в `config.py` (`WEB_ADMIN_USER`, `WEB_ADMIN_PASS`,
`WEB_PORT`).

Остановка — кнопкой в админке или `Ctrl+C` в окне (статистика + сохранение стейта).

## ⏱ Таймлапс — «сутки за час»

Виртуальные часы (`simclock.py`) отвязывают «время отдела» от реального.
Ночи и выходные **проматываются почти мгновенно**, поэтому реальное время
тратится в основном на рабочие часы. Все паузы в коде заданы в
*симулированных* секундах; реальный сон = sim / scale.

Главная ручка в `config.py`:

```python
TIMELAPSE_ENABLED = True

# Сколько РЕАЛЬНЫХ минут занимает один симулированный РАБОЧИЙ день (10–18):
SIM_WORKDAY_REAL_MINUTES = 60     # 60 → рабочий день за час
                                  # 20 → за 20 минут
                                  # 240 → почти реальное течение

# Либо задать масштаб напрямую (sim-секунд за 1 реальную секунду):
TIME_SCALE_OVERRIDE = None        # напр. 24 ≈ сутки/час, 168 ≈ неделя/час

SIM_START = None                  # None = «сегодня 10:00»; либо "2026-06-01 10:00"
FAST_FORWARD_OFFHOURS = True      # проматывать ночи/выходные (суть таймлапса)
API_MIN_PAUSE  = 0.4              # минимальная реальная пауза (вежливость к API)
MAX_REAL_SLEEP = 8.0              # потолок реального сна на одну паузу
```

Чтобы вернуть реальное время — `TIMELAPSE_ENABLED = False`.

В логах действия помечаются симулированным временем (`Mon 2026-06-08 14:23`),
так что прогон выглядит как настоящий журнал рабочего дня/недели.

## Рабочие часы и off-hours

Считаются по симулированному времени. Будни `WORK_HOURS_START..WORK_HOURS_END`
(по умолч. 10–18), выходные — сб/вс.

```python
OFF_HOURS_MODE = "oncall"   # "idle"   — после 18:00 полный стоп до 10:00
                            # "oncall" — изредка дежурный тушит пожары ночью
OFF_HOURS_ACTIVITY_PROBABILITY = 0.04
```

При таймлапсе в режиме `idle` ночь промётывается до 10:00 ближайшего рабочего дня;
в `oncall` — иногда срабатывает дежурный (hotfix/revert/инцидент/триаж), иначе
ночь пролетает кусками.

## Реализм: что делает симулятор похожим на настоящий отдел

- **Жизненный цикл правил** (`state.py`): правила имеют статус, возраст и FP-историю.
  Тюнят именно *шумное* правило, промоутят *давно чистое*, депрекейтят *мёртвое*,
  откатывают и потом *пересоздают исправленную версию*. Состояние переживает рестарт
  (файл `.sim_state.json`).
- **Несовершенство**: CI-пайплайны от `soc-bot` иногда падают (`🔴 failed`) → автор
  пушит fixup → `✅ passed`; часть MR начинается как **Draft**; иногда MR **закрывают
  без мёржа**; реверты бывают **отложенными**.
- **Настоящие GitLab-фичи**: approvals через Approvals API, эмодзи-реакции,
  теги + GitLab Releases + CHANGELOG.
- **Issues и спринты**: баг-репорты на FP, фич-реквесты, intel-задачи с лейблами
  (`severity::high`, `type::bug`…), привязкой к спринт-майлстонам и `Closes #N`.
- **Ритм отдела**: утренние стендапы, ротация on-call, отпуска/болезни (агент
  выпадает на день), пятничный change-freeze (не катим рискованное), границы
  спринтов с релизом.
- **Сюжетные кампании**: одна угроза (CVE/группировка) тянет цепочку — трекинг-тикет
  → threat intel → правило детекта → плейбук → итог и закрытие.

## Логи и состояние

Все действия пишутся в `simulator.log` (ротация 10MB×5). Жизненный цикл и
счётчики — в `.sim_state.json` (можно удалить, чтобы начать «с чистого листа»).
В конце прогона (`Ctrl+C`) выводится статистика по всем типам активностей,
финальное sim-время, число правил и номер спринта.

## Слой данных для ML (журнал событий + аномалии)

Симулятор пишет **размеченный журнал событий** — основу для будущего обучения
детектора аномалий. Никакого ML внутри нет; это только генерация данных.

- **Файл:** `data/events.jsonl` — по одной JSON-строке на каждое действие
  (push, ветка, MR, коммент, merge, approve, issue, аномалия). Накапливается
  между запусками, каждая строка помечена `run_id`.
- **Время:** у каждого события есть `ts_sim` (время симуляции) и `ts_real`,
  а также `hour`, `weekday`, `is_night`, `is_weekend` — корректные временны́е
  признаки, несмотря на то, что коммиты в GitLab штампуются реальным временем.
- **Метки:** `is_anomaly`, `anomaly_type`, `severity`. Подавляющее большинство
  событий нормальные; аномалии очень редки (положительный класс).

### Аномалии (редкие, размеченные)

Управляются в `config.py`: `ANOMALY_RATE` (рабочее время), `ANOMALY_RATE_OFFHOURS`
(ночью выше), `SECRET_RATE_MULT` (делает утечки секретов ещё реже), и словарь
`ANOMALIES` (вкл/вес каждого типа). Типы:

- **Утечки секретов** (очень редко, синтетические, но формат-валидные значения):
  секрет в коммите/`.env`, секрет в `.gitlab-ci.yml` (`echo $SECRET`), секрет в
  комментарии MR, «бэкап» секретов из vault в обычный репозиторий, хардкод токена в коде.
- **Права/обход ревью:** самоаппрув своего MR, merge без ревью, прямой push в
  `main`, ослабление протекции ветки, выдача доступа к `soc-secrets`, создание
  лишнего API-токена.
- **Разрушительные:** массовое удаление файлов.

### Benign-лукалайки (важные hard-negatives)

Активность `benign_quirk` создаёт **похожие на секрет, но нормальные** артефакты:
`.env.example` с плейсхолдерами, тестовые фикстуры с заведомо фейковыми ключами,
base64-ассеты, большие файлы, коммит «не в ту ветку», отладочный `print`. Они
помечены `lookalike`/`quirk` и `is_anomaly=false` — чтобы детектор учился не
путать их с настоящими утечками.

### Где смотреть

В веб-панели появилась вкладка **«Данные · датасет»**: счётчики событий и
аномалий, разбивка по типам, лента последних событий (аномалии — красным,
лукалайки — янтарным) и кнопка скачивания `events.jsonl`.

## Сотрудники, права и репозитории (обновление)

- **Раздел «Сотрудники»** в веб-панели: карточка на каждого, раскрытие →
  живая лента действий (что и куда заливает, время, аномалии). На «Обзоре» у
  каждого участника видно текущее действие.
- **Outer-права на первом старте**: симулятор идемпотентно выдаёт инженерам
  права Owner во всех рабочих репозиториях (`GRANT_OWNER`, `OWNER_ACCESS_LEVEL`,
  `TEAM_USERS`). Если уже выдано — пропускает. Это же чинит права на merge.
- **Автоподхват репозиториев**: на старте находит существующие проекты в
  namespace (`AUTO_DISCOVER_PROJECTS`, `PROJECT_NAMESPACE`) и добавляет их в
  рабочий пул `WORK_REPOS` — обычные сценарии и аномалии распределяются по всем
  репозиториям, не только по шести базовым.
- **Новые аномалии**: `pipeline_token_leak` (кривой CI печатает токены в лог и
  кладёт в артефакт), `disable_pipeline_security` (отключение SAST/secret-
  detection), `artifact_secret_exposure` (креды в артефакте сборки),
  `commit_to_secrets_repo` (прямой коммит секрета в vault-репозиторий),
  `data_exfiltration` (выгрузка большого закодированного архива). Всё — с метками
  в `events.jsonl`, плюс поле `detail` с человекочитаемым описанием инцидента.

## Полный лог прогона, Telegram-отчёты, анти-повтор

- **Полный лог** (`runlog.py`): при каждом запуске создаётся `logs/run-<дата>.log`
  на уровне DEBUG — туда пишется ВСЁ (каждое действие, предупреждения, ошибки,
  трейсбеки). Этот файл удобно прислать на разбор. В веб-панели на вкладке
  «Журнал событий» — кнопка **«Скачать полный лог прогона»** и счётчики
  warnings/errors.
- **Telegram-отчёты** (`telegram.py` + `report.py`): бот шлёт отчёт о старте/
  остановке, периодический отчёт (раз в `report_every_min` реальных минут) и
  алерты на каждую аномалию (с антифлудом). Кнопка **«Отправить отчёт в Telegram»**
  отправляет сводку немедленно. Настройки — `config.TELEGRAM` (`token`, `chat_id`,
  `report_every_min`, `send_anomalies`, `send_start_stop`).
  ⚠️ Чтобы бот мог писать в личку, один раз откройте **@socsimulatebot** и нажмите
  **Start** — иначе Telegram вернёт 403.
- **Анти-повтор**: планировщик не запускает один и тот же тип активности более
  двух раз подряд; `new_detection_rule` не создаёт уже существующее правило;
  набор тем документации расширен. Действия перестают «зацикливаться».

### Про пайплайны
Без зарегистрированного GitLab Runner настоящие пайплайны не выполняются — это
нормально. Наш CI (зелёный/красный билд) **симулируется** комментариями `soc-bot`.
Если фейк-сообщения о падении пайплайнов мешают — поставьте `PROBS["ci_fail"] = 0`
или `FEATURES["ci_pipeline"] = false`.

## Больше сотрудников и репозиториев (динамическая среда)

На **первом старте** симулятор сам поднимает среду (идемпотентно — если уже есть,
пропускает), модуль `bootstrap.py`:

- **Создаёт новых сотрудников** в GitLab (`config.NEW_USERS`) — по умолчанию +6
  человек разных ролей (detection engineer, threat hunter, soc analyst, devops,
  ml engineer). Команда становится ~10 человек, и все они появляются в разделе
  «Сотрудники».
- **Создаёт новые репозитории** в группе (`config.NEW_REPOS`): `threat-hunting`,
  `cloud-detections`, `siem-content`, `edr-integration`, `soc-automation`,
  `incident-response`. Плюс подхватывает уже существующие.
- **Распределяет работу по репозиториям**: детект-активности идут в `RULE_REPOS`,
  парсеры — в `PARSER_REPOS`, плейбуки — в `PLAYBOOK_REPOS`. Теперь команда
  работает не только в `detection-rules`.
- Выдаёт всем участникам **Owner** во всех репозиториях.

Управление — в `config.py`: `CREATE_USERS`, `CREATE_REPOS`, `NEW_USERS`,
`NEW_REPOS`, `RULE_REPOS` / `PARSER_REPOS` / `PLAYBOOK_REPOS`.

> Для создания пользователей и репозиториев нужен **admin**-токен GitLab. Если
> новые юзеры/репо не появились — посмотрите `logs/run-*.log`: там будет причина
> (нет admin-прав, нет свободных мест-лицензий, группа не найдена и т.п.).
