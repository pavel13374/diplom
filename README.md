# Sentinel — автоматизированное обнаружение угроз в процессе разработки

Стенд из двух половин, которые ничего не знают друг о друге напрямую и общаются
только через общий журнал событий:

- **Среда** (`:8787`) — живой отдел разработки в GitLab. Сотрудники пишут код,
  открывают merge request'ы, ревьюят друг друга, ходят в отпуска и дежурят.
  Иногда среди них действует злоумышленник.
- **Консоль защиты** (`:8788`) — рабочее место аналитика SOC. Читает тот же
  журнал, поднимает детекты, собирает их в инциденты, раскладывает по матрице
  MITRE ATT&CK и помогает довести расследование до отчёта.

Смысл работы — проверить, можно ли обнаружить вредоносную активность внутри
процесса разработки, **не имея разметки**: детектор видит ровно то же, что видел
бы настоящий SOC, — поток событий git и CI, без единой подсказки о том, где
атака.

---

## Быстрый старт (Windows)

```
START.bat
```

Поднимает обе консоли в отдельных окнах и открывает браузер.
`STOP.bat` — остановить. Пароль администратора берётся из переменной окружения
`SOC_ADMIN_PASS`; если она не задана, при старте генерируется случайный и
печатается в консоль.

Вручную:

```
python webapp.py        # среда, http://127.0.0.1:8787
python console.py       # защита, http://127.0.0.1:8788
```

Без доступа к GitLab стенд работает в автономном режиме: `SOC_OFFLINE=1`.
События при этом пишутся в журнал как обычно, наружу ничего не уходит.

Настройки живут в `web_config.json`. В репозитории его нет — он содержит токен
доступа к GitLab; рядом лежит `web_config.example.json` с той же структурой и
пустым токеном. Скопируйте его и впишите свой.

### Переменные окружения

| переменная | по умолчанию | смысл |
|---|---|---|
| `SOC_ADMIN_USER` / `SOC_ADMIN_PASS` | `admin` / случайный | вход в обе консоли |
| `SOC_WEB_HOST` | `127.0.0.1` | адрес привязки консолей. В контейнере обязателен `0.0.0.0`, иначе опубликованные порты недостижимы |
| `SOC_WEB_PORT` / `SOC_CONSOLE_PORT` | `8787` / `8788` | порты консолей |
| `SOC_SESSION_HOURS` | `8` | срок жизни сессии |
| `SOC_GITLAB_TOKEN` (или `GITLAB_ADMIN_TOKEN`) | из `.gitlab_token` | админский PAT GitLab |
| `SOC_GITLAB_VERIFY_TLS` | `auto` | проверка сертификата GitLab: `auto` \| `on` \| `off`. В режиме `auto` решение принимается по адресу — для локальной сети (`192.168.*`, `10.*`, `172.16–31.*`, `localhost`, `*.local`, короткое имя хоста) проверка выключается, для публичного домена включается |
| `SOC_GITLAB_CA_BUNDLE` | — | путь к своему CA-бандлу: правильный способ работать с самоподписанным сертификатом, работает и в лаборатории (важнее режима) |
| `SOC_TELEGRAM_TOKEN` / `SOC_TELEGRAM_CHAT_ID` | из `.telegram_token` / `.telegram_chat` | отчёты в Telegram; без них выключены |
| `SOC_OFFLINE` | — | мир пишет события без обращения к GitLab |
| `SOC_DEBUG` | — | уровень DEBUG в файловые журналы |
| `SOC_DEBUG_ERRORS` | — | отдавать текст исключения в теле HTTP-ответа (по умолчанию наружу уходит только идентификатор) |

### Безопасность контура

Обе консоли рассчитаны на запуск **на машине аналитика**, за петлевым
интерфейсом, с одной общей учётной записью. Это не многопользовательская
система: ролей нет, разграничения доступа нет, аудита действий аналитика нет.

Что при этом сделано, потому что «слушает только 127.0.0.1» — не граница
безопасности (браузер аналитика тоже находится на 127.0.0.1):

* изменяющие запросы требуют заголовок `X-CSRF-Token` (двойная отправка);
* cookie сессий у консолей разные (`sentinel_env`, `sentinel_console`) — иначе
  они перетирают друг другу атрибуты, потому что cookie не разделяются по портам;
* админский токен GitLab маскируется в `/api/config` и в диагностической выгрузке;
* адрес GitLab проверяется при записи: только `http`/`https`, без учётных данных
  в URL, без link-local и адресов метаданных облака;
* выгрузка журнала событий ограничена каталогом `data/`;
* ограничение подбора пароля — по источнику запроса, с растущей паузой.

`docker compose up` публикует порты **только на 127.0.0.1 хоста**, а пароль
генерируется при старте и печатается в лог контейнера.

Идентификаторы репозиториев **не хардкодятся**: на старте автодискавери находит
настоящие id и кладёт в рабочий пул, а `config.repo_id(имя)` — единственная
точка их разрешения. Раньше часть активностей читала статическую карту
`PROJECTS` напрямую, и после пересоздания репозиториев они молча били в
несуществующие id — 571 отказ за прогон без единой строки в логе.

Отдельно — статическая проверка правил и замер их точности:

```
python tools/lint_rules.py     # правила не читают метку, техники в модели угроз
python tools/rule_quality.py   # точность каждого правила и вклад в шум
```

## Воспроизведение за пять минут

Ниже — путь от `git clone` до цифр. На каждом шаге указано, **что должно
получиться**: если получилось другое, это и есть место, где сломалось.

### 0. Зависимости

```
pip install -r requirements.txt
```

`numpy` и `scikit-learn` необязательны: без них обучение идёт на чистом Python
(медленнее, результат тот же — оба пути считают один и тот же полнобатчевый шаг).

### 1. Проверка окружения

```
python tools/doctor.py
```

Ожидается: правил `39`, словарь наблюдаемых действий непустой, анти-лик
включён. Раздел «Обращения к GitLab» на свежем клоне пуст — журнала ещё нет.

### 2. Проверка стенда

```
python run_tests.py
```

Ожидается **17/17 зелёных**. Красный `generated-content` означает, что сломан
генератор содержимого — то, что уходит в репозитории GitLab; это блокирующая
ошибка, стенд будет писать мусор.

### 3. Обучение модели слоя L2

```
python research/train_runtime_model.py --seeds 3
```

Занимает 1–2 минуты. Ожидаемые порядки величин (точные числа зависят от сида):

| Метрика | Ожидание | Что означает |
|---|---|---|
| PR-AUC | 0.22–0.26 при базе ≈0.030 | выигрыш над случайным в 8–9 раз |
| ROC-AUC | 0.84–0.88 | приводится для сравнимости, решение по PR-AUC |
| ECE | ≈ 0.012 | заявленная вероятность совпадает с наблюдаемой частотой |
| Brier Skill Score | > 0 | модель информативнее константы |
| потеря ранга у Платта | ровно 0.0% | строго монотонная калибровка не меняет порядок |
| событийная precision | 85–90% | при бюджете ложных 0.05% |
| эпизодов в test | 70+ | меньше — интервалы станут бесполезно широкими |

Скрипт печатает разбивку recall по семействам атак и сравнение с сигнатурным
baseline. Модель ложится в `models/runtime_model.json` и подхватывается
детектором при следующем старте.

### 4. Вклад слоёв со значимостью

```
python research/ablation.py --seeds 2 --days 14
```

Ожидается: полный стек значимо полнее одних сигнатур (`full vs rules_only`,
p < 0.05 после поправки Холма), вклад слоя ML значим, вклад поведенческого
слоя на этом объёме — на грани. Таблица идёт в главу «эксперименты» как есть.

### 5. Выбор рабочей точки

```
python research/workload_curve.py --capacity 10
```

Строит кривую «полнота против нагрузки на аналитика» и рекомендует порог под
заданную ёмкость смены. График — `results/workload_curve.svg`, он же виден в
консоли защиты в разделе «Тренды».

### 6. Запуск стенда

```
python webapp.py        # среда,  http://127.0.0.1:8787 — нажать «Запустить»
python console.py       # защита, http://127.0.0.1:8788
```

Через минуту в консоли защиты растут счётчики событий. Если они стоят на нуле,
смотри плашки наверху: «Мир молчит» — не запущена среда, «Хранилище событий
недоступно» — отказ базы (причина написана там же).

### 7. Атака и разбор

Консоль защиты → **Red Launcher** → выбрать кампанию → запустить.
Через несколько секунд: детекты в «Алертах», собранный инцидент в «Инцидентах»
с восстановленной цепочкой ATT&CK. Открыть инцидент → «LLM-разбор» (или
детерминированный разбор, если Ollama не запущена) → выставить вердикт.

### 8. Итоговые метрики

```
python metrics.py
```

Ожидается: detection rate с интервалом Уилсона, MTTD с указанием, по скольким
эпизодам он посчитан, покрытие ATT&CK около 72%, PR-AUC рядом с базой класса.

## Что система НЕ делает

Раздел существует, чтобы нормальное поведение не выглядело поломкой.

**`soc-secrets` почти пуст — так и задумано.** Это хранилище секретов: по
замыслу туда ходят только атаки (`commit_to_secrets_repo`, `secret_exfil_vault`).
Десяток событий за прогон против четырёх тысяч у `detection-rules` — не
недоработка, а модель угроз.

**Поведенческий слой молчит первые сотни событий.** Пока в профиле актора
меньше 30 событий, а в резервуаре калибровки меньше 400 наблюдений, порог равен
бесконечности и слой не срабатывает вообще. Это осознанно: на пустой истории
неожиданно всё, и фиксированный порог давал лавину ложных тревог именно там,
где данных меньше всего.

**В сумму неожиданности входят не все компоненты.** Только `repo` и `hour`.
Компоненты `action` и `burst` считаются и показываются в объяснении, но в скор
не идут: неожиданность является мерой улики лишь при равномерной альтернативе,
а для этих двух допущение нарушено по построению задачи. Замер — в
`tools/ueba_components.py`, разбор — в докстринге `detector.UEBA`.

**Слой ML чаще молчит, чем кричит.** Он поднимает приоритет, когда согласен с
правилом или поведенческим слоем, и лишь изредка создаёт тревогу сам. Порог
подобран под бюджет ложных срабатываний 0.05%; при таком бюджете событийный
TPR порядка 6–7% — это не поломка, а цена точности 80%+.

**Покрытие ATT&CK — 72%, и оно не должно быть 100%.** Знаменатель — модель
угроз контура разработки (46 техник), а не список техник, под которые правила
уже написаны. Тринадцать слепых зон — очередь работ, а не дефект.

**Метки атак не используются при обнаружении.** Ни на одном шаге. Разметка
живёт в другом слое и применяется исключительно постфактум, при подсчёте
точности. Это проверяется двумя тестами (`antileak`, `leakage`) и сторожем
словаря действий в `events.emit()`.

**Без GitLab стенд работает.** `SOC_OFFLINE=1` — события пишутся в журнал,
наружу ничего не уходит, детектор работает как обычно. Плитка «GitLab» на
странице диагностики в этом режиме показывает `offline`, а не «на связи»:
консоль защиты к GitLab не обращается по устройству и не может утверждать
ничего о его состоянии.

**Заглушка определяется по каждому совпадению, а не по файлу.** Признак
`placeholder_signal` раньше означал «где-то в файле есть слово example/todo» и
требовался четырьмя правилами со значением `false`. Одна строка `# TODO`
рядом с настоящим токеном роняла риск с 0.92 до 0.00. Теперь решение
принимается по самому совпавшему фрагменту и его строке, а `n_real_hits`
считает сигнатуры, сработавшие на не-заглушках. Файл, названный шаблоном
(`.env.example`, `config.dist`), по-прежнему молчит на низкоэнтропийных
примерах — но настоящий высокоэнтропийный токен в нём обнаруживается.

**Секрет ищется и в нормализованном виде.** Склейка строковых литералов,
перенос обратным слэшем, `\xNN`/`%NN`-escape, символы нулевой ширины,
кириллические двойники латиницы и base64 снимаются вторым проходом. Сам факт,
что сигнатура проявилась только после нормализации, — отдельная улика
(`evasion_signal`, правило `secret-obfuscated-evasion`): обычный код не прячет
свои строки.

**Анализ содержимого ограничен по объёму.** Файлы больше 1 МиБ разбираются по
голове и хвосту, результат помечается `truncated`, и правило
`content-not-fully-scanned` сообщает об этом аналитику. Размер файла выбирает
автор коммита, а разбор синхронен внутри конвейера — без потолка один коммит
останавливал бы проверку всего потока.

**Базовая линия поведения не учится на собственных тревогах.** Наблюдение, на
котором сработало правило, в профиль актора не идёт, счётчики профиля стареют,
а число невзятых наблюдений видно на странице «Сущности». Без этого подготовка
из двухсот безобидных ночных обращений делала последующую операцию обычной для
слоя UEBA.

## Реальный мониторинг — «поймай меня сам»

Стенд не только проигрывает свои сценарии — он следит за **настоящим** GitLab.
Наблюдатель `tools/gitlab_watch.py` опрашивает Events API, берёт diff каждого
нового коммита, считает те же признаки содержимого (энтропия, secret-regex, имя
файла) и пишет `push`-событие в общий журнал — **без единой метки симулятора**.
Детектор на `:8788` разбирает его наравне с остальными.

```
watch_gitlab.bat        # или: python tools/gitlab_watch.py
```

Проверка вживую: при запущенном наблюдателе закоммитьте руками в свой GitLab
файл с секретом (например, `config/prod.env` со строкой вида
`GITLAB_TOKEN=glpat-…`). Через несколько секунд на консоли защиты появится
алерт по технике T1552 (Credential Access) и заведётся инцидент — система
поймала утечку по наблюдаемым признакам, а не по подсказке.

Ровно этот путь без сети проверяет набор `realmon`: он собирает событие точно
как наблюдатель, прогоняет через детектор и коррелятор и требует алерт +
инцидент, а чистый коммит без секретов оставляет без тревоги.

## Как это устроено

```
Среда (webapp.py)                  Журнал событий            Защита (console.py)
  агенты, планировщик   ──пишет──▶   event-store   ──читает──▶  детектор → корреляция
  GitLab REST API                    SQLite, WAL                правила + UEBA → инциденты
                                     курсор чтения              ATT&CK, LLM-триаж, отчёты
```

Ключевое ограничение, на котором держится вся честность эксперимента: **защита
никогда не видит меток симулятора**. Она получает только наблюдаемые поля —
кто, когда, в каком репозитории, что сделал. Метка «это была атака» живёт в
другом слое и используется исключительно постфактум, при подсчёте точности.

Одного вырезания полей разметки для этого мало. Раньше каждый шаг атаки эмитил
собственное «говорящее» действие — `steal_oauth`, `repo_enum`, `mass_delete`, —
которого у обычных сотрудников не бывает. Поля разметки при этом были честно
срезаны, но правило вида `{"action": "steal_oauth"}` не обнаруживало атаку, а
читало ответ под другим именем.

Поэтому введён **нормализованный словарь действий** (`taxonomy.py`): и обычная
работа, и атака описываются одними и теми же действиями, какие видны в аудит-логе
GitLab, а различаются только наблюдаемыми атрибутами. «Кража OAuth-токена» — это
теперь `api_read(api_path="/oauth/tokens")`, ровно то, что увидел бы настоящий
SOC. Отличить это от легитимного обращения можно только по частоте, времени и
связке с другими событиями — то есть детектор обязан детектировать.

Гарантия анти-лика: для каждого наблюдаемого признака
считается взаимная информация с меткой (с поправкой на кардинальность через
перестановки), и ни одно значение не должно встречаться только у атаки.

### Слои обнаружения

| Слой | Что ловит | Чем силён |
|---|---|---|
| Обогащение | скользящие агрегаты по актору: всплески удалений, интенсивность API-чтений, охват репозиториев | без него «массовость» и «разведка» неотличимы от единичного нормального действия |
| L0 Detection-as-Code | известные приёмы: секрет в коммите, merge без ревью, ослабление branch-protection | точность, объяснимость, готовый маппинг на ATT&CK |
| L1 UEBA | отклонения от привычного поведения: скор = неожиданность события **в битах** | порог выводится из данных под бюджет тревог, а не назначается константой |
| L2 ML | то, под что правило ещё не написано; обобщается на форматы секретов, которых не видел | линейная модель: вклад каждого признака в скор раскладывается ТОЧНО (`MLScorer.explain`), калибровка выбирается замером — Платт или изотоника |
| Корреляция | склейка разрозненных детектов одного актора в инцидент с kill-chain | превращает шум в историю атаки |
| LLM-триаж | человеческий разбор инцидента и приоритет | снимает рутину с аналитика; при недоступности модели работает детерминированный разбор |

Слияние рисков — **сложение СВИДЕТЕЛЬСТВ в лог-шансах**:

```
logit R = logit π + Σ γ^i · (logit pᵢ − logit π)
```

где π — базовая частота атак, γ — затухание для зависимых источников. Слои
отдают апостериорные оценки, в которые приор уже входит; чтобы получить чистое
свидетельство слоя, приор вычитается. Без вычитания он складывался бы n раз, и
при низком приоре каждый ДОПОЛНИТЕЛЬНЫЙ слой понижал бы риск — правило 0.70 плюс
подтверждение модели 0.03 давало на выходе 0.30. Свойство «согласие слоёв не
может понижать риск» закреплено тестом.

На уровне инцидента применяется то же слияние, но по МАКСИМУМАМ КАЖДОГО СЛОЯ:
многошаговая кампания растянута по событиям, и пособытийное слияние никогда не
встретит свидетельство правила о шаге 1 со свидетельством поведенческого слоя о
шаге 3.

Модель слоя L2 **лежит в репозитории** (`models/runtime_model.json`, около 60 КБ)
и полностью воспроизводится:

```
python research/train_runtime_model.py    # -> models/runtime_model.json
```

Раньше она была в `.gitignore`, и на свежем клоне слой L2 молча выключался —
проверяющий видел систему без её ключевой части при том, что вся работа про ML.
Файл содержит ещё и метрики, на которых обучен, то есть является артефактом
эксперимента. Если файла нет или он несовместимого формата, слой выключается с
предупреждением в лог и командой переобучения.

39 правил лежат в `detections/*.json` — обычные файлы, их можно править и
добавлять без перезапуска логики: правило описывается декларативно.

### Как читать метрики

Все доли приводятся с доверительными интервалами (Уилсон 95%), MTTD — с
bootstrap-интервалом. Точечная оценка без интервала создаёт ложную точность:
«recall 74.5%» на 55 эпизодах — это на самом деле «где-то между 61 и 85%».

Основная интегральная метрика — **PR-AUC**, а не ROC-AUC. При доле атакующих
событий порядка процента ROC-AUC выглядит прекрасно даже у слабого детектора,
потому что знаменатель FPR — огромное число нормальных событий. Базовый уровень
PR-AUC равен доле положительного класса, поэтому его и надо держать рядом с
цифрой.

Сравнения конфигураций детектора проверяются **тестом Макнемара** на парных
исходах по одним и тем же эпизодам, с поправкой Холма на множественные
сравнения. «Различие незначимо» — честный результат, а не неудача.

Готовые эксперименты:

| Скрипт | Что отвечает |
|---|---|
| `research/ablation.py` | вклад каждого слоя со значимостью: full / no_ml / no_ueba / rules_only, Макнемар + Холм, PR-AUC с bootstrap-интервалом |
| `research/workload_curve.py` | полнота против нагрузки на аналитика; рекомендует порог под ёмкость смены, рисует SVG |
| `tools/ueba_components.py` | какая компонента неожиданности несёт сигнал, а какая работает против; проверка допущения о пуассоновости потока |
| `research/rule_baseline.py` | сигнатурный baseline на эпизодном уровне |

Калибровка выбирается **замером, а не по вкусу**: обучаются и Платт, и
изотоническая регрессия, побеждает та, у которой меньше ECE — но только среди
тех, что не теряют больше 5% ранжирующей способности. Ограничение обязательно:
изотоника почти всегда калибрована лучше, но её плоские участки склеивают разные
маржи в одну вероятность, а очередь аналитика отсортирована по риску. Строго
монотонный Платт теряет ровно 0.0% — это проверяется численно на каждом
обучении.

### Как считается покрытие ATT&CK

Матрица в консоли — это **модель угроз контура разработки**: 46 техник MITRE
ATT&CK Enterprise, которые в принципе наблюдаемы по событиям git, CI/CD и
GitLab API. Правила закрывают 33 из них, то есть покрытие — около 72%,
а остальные 13 честно горят как слепые зоны и образуют очередь работ для
detection engineering.

Это сделано намеренно. Если положить в матрицу только те техники, под которые
правила уже написаны, покрытие всегда будет 100% — метрика начнёт измерять
сама себя и потеряет смысл. Техники, принципиально ненаблюдаемые в этом
контуре (фишинг, эндпоинт, сетевой уровень), в матрицу не включены: их
отсутствие — граница системы, а не пробел в правилах.

## Разделы консоли защиты

**Обзор** — состояние платформы, живая лента детектов, очередь инцидентов,
покрытие ATT&CK, качество детектирования по подтверждённым вердиктам.

**Алерты** — таблица потока: поиск, сортировка, фильтры, постраничный вывод,
карточка детекта сбоку.

**Инциденты** — рабочее место расследования: таймлайн, доказательства,
связанные детекты, разбор моделью, техники ATT&CK, действия и заметка аналитика.

**Дела** — несколько инцидентов объединяются в одно расследование:
ответственный, статус, приоритет, история действий, печатная сводка.

**Очередь триажа** — приоритет, SLA, вердикты TP/FP с клавиатуры.

**ATT&CK Coverage** — матрица покрытия с переходом из техники в инциденты и
выгрузкой слоя для ATT&CK Navigator.

**Детекты** — каталог правил: что сработало, что молчит, карточка правила.

**Сущности** — поведенческие профили: что для человека норма и насколько
сегодняшний день от неё отличается.

**Профиль риска** — рейтинг разработчиков и репозиториев по риску и динамика во
времени. Оценка складывается из пикового и среднего риска, объёма детектов,
разнообразия техник и числа инцидентов.

**Red Launcher** — запуск атакующих кампаний: от разведки до выгрузки.

**Реплей прогона** — весь прогон как запись: детекты, тактики и инциденты на
одной шкале с курсором и воспроизведением.

**Тренды** и **Диагностика** — метрики во времени и техническое состояние.

## Обратная связь аналитика

Вердикты TP/FP — не украшение. Они переживают перезапуск (идентификаторы
инцидентов детерминированы), из них считается живая точность детектирования, а
правило, трижды помеченное как ложное срабатывание, автоматически уходит в
приглушённые и перестаёт засорять очередь. Это видно на дашборде: сколько
инцидентов разобрано, какая точность, какие правила шумят.

При старте консоль переигрывает последние события из журнала и восстанавливает
картину — инциденты и вердикты не теряются между запусками.

## Интерфейс

Три темы: тёмная (по умолчанию, язык SIEM/XDR), светлая и яркая — переключаются
кнопкой в верхней панели, выбор запоминается. Рядом переключатель языка RU/EN:
переводится оболочка продукта, а имена разработчиков, названия репозиториев и
тексты из журнала остаются как есть — это данные, их не переводят. Есть
командная палитра по `Ctrl+K` и сворачиваемое меню.

Обе консоли собраны на одной дизайн-системе (`static/design-system.css`). Три
правила, которые в ней соблюдаются жёстко:

- цвет нигде не задаётся напрямую, только через семантические токены;
- капс — только в шапках таблиц, подписи набираются обычным регистром;
- любая пара «текст на фоне» держит WCAG 2.1 AA, и это считается тестом, а не
  проверяется на глаз.

Интерфейсом можно пользоваться без мыши: навигация получает фокус табом,
у иконок есть подписи для скринридера, уровень критичности различается не
только цветом, но и формой значка, а анимации отключаются при системной
настройке «меньше движения».
