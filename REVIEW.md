# Полный аудит проекта

**Дата:** 2026-08-29 · **Тип:** приёмочный аудит перед защитой
**Объект:** SOC-симулятор (мир «Sentinel Env» :8787 + консоль защиты «Sentinel SOC» :8788)
**Метод:** белый ящик (исходники) + чёрный ящик (работающий стенд через браузер) +
серый ящик (сверка показаний экрана с кодом и базой)

Все числа в отчёте получены исполнением: запросом к API работающего стенда,
SQL по базе `data/events.db` либо прогоном кода. Там, где проверить не удалось,
стоит **НЕ ПРОВЕРЕНО** с объяснением причины.

## Executive Summary

Проект работает и держит сквозную цепочку
«действие разработчика → событие → детект → алерт → корреляция → инцидент →
разбор аналитиком → вердикт → статистика» — это подтверждено не чтением кода,
а приёмочным прогоном: через штатный «Запуск сценариев» поставлено и исполнено
**30 красных кампаний** (114 шагов, 30 техник ATT&CK), они дали **23 новых
инцидента**, все **56** инцидентов разобраны и закрыты с вердиктами
(**37 TP / 19 FP**), состояние переживает перезагрузку страницы и лежит в базе.

Главный результат аудита — **две слепые зоны ATT&CK, которые числились
покрытыми**. Обе найдены статически и независимо подтверждены приёмочным
прогоном (техника исполнена красной командой — детект не сработал ни разу):

| Техника | Правила | Почему не срабатывало |
|---|---|---|
| **T1562** Impair Defenses | `merge-without-approval`, `self-merged-mr` | поле `approvals_count` не попадает **ни в одно** событие `mr_merge` (0 из 6013): код читал его из объекта MR, а в GitLab API оно живёт в отдельной ручке `/approvals` |
| **T1087** Account/Repo Discovery | `recon-enumeration` | сценарий выдаёт ровно 5 запросов `api_read`, правило требует всплеска ≥ 8: пороги подняли по замеру точности, объём сценария — нет |

Измеренная полнота детектирования по приёмочному прогону: **28 из 30 техник = 93.3%**.
Обе недостачи — ровно эти две техники. Причины устранены (FIX-1, FIX-2), правки
проверены модульно; **живая проверка требует перезапуска мира**, который из среды
аудита выполнить нельзя.

Фальшивых метрик — подставленных чисел, демо-данных на боевом пути отображения,
захардкоженных процентов — **не найдено**. Показатели считаются из реальных
данных, и почти все сходятся с независимым пересчётом. Найденные расхождения —
это несовпадение подписи и содержания либо разные окна выборки на соседних
панелях, а не подделка.

Тесты: **21 из 21 PASS**, пропусков нет (два пропускавшихся набора запущены
после установки `jsdom`).

**Итог: PASS WITH MINOR RISKS.** С оговоркой: до перезапуска мира два дефекта
уровня High остаются активными в работающем стенде — исправления лежат в коде,
но процесс исполняет версию, загруженную при старте.

## Архитектура проекта

Два независимых Flask-приложения над общим event-store (SQLite, WAL):

```
МИР (webapp.py, :8787)                  ЗАЩИТА (console.py → console_app/, :8788)
  scheduler.py                            ingest.py  (фоновый поток)
  agents/ (20 персонажей)                   ↓
  activities/ (51 активность)             detector.py   L0 правила (41) +
  gitlab_client.py → GitLab 19.0.1                      L1 UEBA + L2 ML + fusion
        ↓                                   ↓
  events.py → eventstore.py  ──────────►  correlator.py → инциденты (в памяти)
        data/events.db                      ↓
        (events, cursors, commands,       incident_status (в базе: вердикты)
         incident_status, metrics_history)   ↓
        ◄── очередь команд ────────────  attack.py (Red Launcher)
```

**Точки входа:** `webapp.py:main()`, `console.py:main()`, `run_defense.py`,
`main.py`/`run_world.py` (CLI), `run_tests.py`.

**Что где живёт (проверено):**

| Сущность | Где | Переживает рестарт |
|---|---|---|
| События | таблица `events` | да |
| Курсор ингеста | таблица `cursors` | да |
| **Алерты** | **только в памяти консоли** (`_STATE["alerts"]`) | **нет** |
| **Инциденты** | **только в памяти** (`correlator`) | **нет**, пересобираются реплеем |
| Вердикты TP/FP | таблица `incident_status` | да |
| Команды красной команды | таблица `commands` | да |
| История метрик | `metrics_history` | да |

Таблица `alerts` в схеме есть, но **пуста (0 строк)** и не используется:
алерты пишет не консоль. Это не дефект работы, но мёртвая схема.

**Ключевое архитектурное решение, которое надо понимать при защите:**
`console_app/core.py:281 REPLAY_EVENTS = 6000`. При старте консоль
переигрывает последние ~6000 событий, восстанавливая алерты и инциденты в
памяти; окно округляется вниз до границы блока в 1500 событий, чтобы
идентификаторы инцидентов (хэш от актора и времени начала) не «плыли» при
каждом перезапуске. Отсюда: показатель «ОБРАБОТАНО ЗАЩИТОЙ» (12 924)
принципиально меньше «СОБЫТИЙ В СТОРЕ» (79 340) — это две разные величины, и
экран честно показывает их двумя разными карточками.

## Движок детектирования

41 правило (`detections/*.json`), плюс поведенческие слои UEBA и ML.
Слои реальны и все три дают срабатывания — проверено на живом стенде:
из 167 алертов **130 — правила, 17 — модель, 3 — UEBA** (по последним 150,
см. дефект STAT-1).

**Анти-лик проверен и работает.** `run_defense.observed()` срезает разметку
мира перед детектором; тесты `antileak` и `leakage` это подтверждают и
проходят. Детектор не видит `is_anomaly` и меток сценария — то есть показатель
детектирования не круговой.

**Прогон по всему журналу** (62 680 наблюдаемых событий, ровно один вызов
`process()` на событие): 349 событий с алертом, 568 срабатываний, 333 эпизода
атак, из них обнаружено 235 → **detection rate 0.706**.

**Мёртвых правил не найдено**, но найдены два, которые не могут сработать в
принципе, — см. раздел ATT&CK. Отдельно проверено и **опровергнуто** первое
подозрение: правила `high-entropy-push` и `ci-debug-token-leak` не срабатывали
на историческом корпусе не из-за дефекта, а потому что признаки
`n_real_hits` / `ci_debug_signal` появились в потоке только с 2026-08-21; на
свежих данных оба срабатывают (13 и 2 раза на последних 6000 событиях).
Это важно для защиты: прогон детектора по старому журналу систематически
занижает часть правил.

**Качество детектирования.** Самое шумное правило — `ml-content`: 85
срабатываний, 32 TP, 14 FP. Оно же единственное, породившее подтверждённые
ложные инциденты. Механизм заглушения шумных правил считает и TP, и FP, поэтому
`ml-content` при 14 FP **не заглушено** (32 TP перевешивают) — проверено:
`muted: []`, `muted_hits: 0`. Логика заглушения корректна.

## Симуляция атак

15 многошаговых кампаний красной команды (`red_team.CAMPAIGNS`), 3 профиля
уклонения (`noisy`/`stealthy`/`adaptive`), 3 темпа. Управление — через очередь
команд в базе: консоль ставит команду, мир её забирает и исполняет.
Просроченные команды (TTL 900 с) снимаются, чтобы свежий запуск не вставал в
хвост старой очереди.

**Проверено исполнением:** 30 запусков (команды `#98`–`#127`) — **30 из 30
выполнены** (`status: done`, «4/4 steps» / «3/3 steps»), 114 шагов, ни одной
ошибки и ни одного просроченного запуска. Задержка от постановки до исполнения
менее минуты.

Сценарии не декоративны: каждый шаг пишет наблюдаемые события в общий журнал,
и эти события доходят до детектора — что и подтверждается 23 новыми инцидентами.

**Время симуляции проверено:** ускорение ×48 заявлено и фактически применяется
(при `SIM_WORKDAY_REAL_MINUTES = 10` рабочий день 8 ч даёт ровно ×48); экран
мира показывает три часа раздельно — время симуляции, реальное время машины и
время GitLab. Расхождений и «времени из будущего» не обнаружено.

## Покрытие MITRE ATT&CK

**Откуда берётся знаменатель.** `attack_matrix.py` — жёстко заданная матрица
проекта: 47 ячеек, **46 уникальных техник** (T1098 «Account Manipulation»
законно стоит в двух тактиках — Persistence и Privilege Escalation).

**Как считается процент.**
`console_app/overview.py:47` — `covered ∩ matrix / |matrix|`, где `covered` —
техники, на которые есть хотя бы одно правило.
**33 / 46 = 71.7% → 72%.** Это показатель ПОКРЫТИЯ ПРАВИЛАМИ, а не доли
обнаруженного: он статичен и не меняется от того, что система детектирует.
На экране «Тренды» подпись это честно объясняет — «Доля техник матрицы, на
которые есть хотя бы одно правило». На «Обзоре» та же цифра стоит без
пояснения рядом с «техник сработало: 31» (дефект UI-2).

Проверено отдельно: и карточки на экране ATT&CK, и строка легенды, и
`/api/stats` считают по **уникальным** техникам, а не по ячейкам
(`covSummary`, `pollAttack` в `dashboard.html` — с явными комментариями про
T1098). Первоначальное подозрение на расхождение 47/46 **не подтвердилось**.

## Проверка сквозного цикла на 30 инцидентах

**Что сделано.** Через штатный экран «Запуск сценариев» (`POST /api/red/launch`,
с CSRF-заголовком, как это делает интерфейс) поставлено **30 кампаний**:
все 15 типов, каждый минимум дважды, с разными профилями уклонения и темпом.
Все 30 исполнены миром (команды `#98`–`#127`, статус `done`), 114 шагов.

**Почему 30 атак дали 23 новых инцидента — точное объяснение.**
Корреляция группирует алерты по актору в пределах временного окна. Мир выбирает
актора для кампании случайно, и 30 кампаний легли на **10 акторов**
(olga.novak — 6, nikita.orlov — 6, pavel.morozov — 4, dmitry.kozlov — 4,
sergey.volkov — 3, anna.smirnova — 3, maria.ivanova — 2, elena.kuzmina — 2,
irina.belova — 1, alex.petrov — 1). Кампании, попавшие на одного актора внутри
окна, склеиваются в один инцидент — именно поэтому в списке есть инциденты с
15–17 алертами и 10–13 разными правилами. Это не потеря данных: сумма шагов
сохранена, объединение — заявленное поведение коррелятора.

**Полнота детектирования по прогону.** 30 кампаний исполнили **30 различных
техник** ATT&CK, все 30 присутствуют в матрице проекта. Сработало **28**.
Не сработали ровно **T1087** и **T1562** — те самые две слепые зоны.

> **Полнота = 28/30 = 93.3%.** После FIX-1 и FIX-2 ожидается 30/30;
> **НЕ ПРОВЕРЕНО** до перезапуска мира.

## Безопасность

Проверено на работающем стенде, а не по описанию.

**Что сделано хорошо:**
- Доступ закрыт **по умолчанию**: `before_app_request` защищает любой новый
  маршрут автоматически, без декоратора, который легко забыть. Проверено:
  без сессии `/api/*` → `401 JSON`, страницы → редирект на вход.
- **CSRF** — двойная отправка cookie, обязательный заголовок `X-CSRF-Token`.
  Проверено: запрос без заголовка отклонён с `403`.
- **Заголовки безопасности** проставляются на все ответы:
  `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`.
- **Ограничение подбора пароля по источнику** (`websec.LoginGuard`), сравнение
  паролей — `hmac.compare_digest` (устойчиво ко времени).
- **Валидация входа** на изменяющих ручках: закрытые наборы значений для
  `status` и `verdict`, ограничение длины `reason` и `owner`, проверка ключа
  кампании и профиля уклонения. Обхода пути через эти параметры нет.
- Наружу отдаётся **идентификатор ошибки**, а не текст исключения (в тексте
  были бы пути на диске и адрес GitLab).
- Пароль администратора **не печатается**, если задан оператором.
- Проверка TLS к GitLab включена и настраиваема; `ssl_verify=False` во всех
  точках создания клиента убран (видно по комментарию и коду `config.gitlab_verify()`).
- Ранее закрытый вектор чтения произвольного файла через `EVENT_LOG.file` из
  веб-конфига **подтверждён закрытым**: настройка больше не применяется, о чём
  приложение сообщает при старте.

**Секреты.** В `web_config.json` лежит рабочий админский PAT GitLab
