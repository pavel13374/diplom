## 1. Краткий вывод

Проект сильный по замыслу и по инженерной культуре: нормализованный словарь действий,
осознанный анти-лик, вероятностный UEBA на surprisal, доверительные интервалы вместо
точечных оценок, тест на взаимную информацию признаков с меткой. Такой уровень
рефлексии для дипломной работы редкость — комментарии в коде объясняют *почему*, а не
*что*, и это видно.

Но между **замыслом и реализацией был разрыв**, и он проходил ровно по тем местам,
которые являются предметом работы.

**Три дефекта уровня «продукт не работает»:**

| № | Дефект | Следствие |
|---|--------|-----------|
| 1 | 15 генераторов содержимого потеряли префикс `f` | **Всё**, что заливалось в GitLab, — Sigma-правила, плейбуки, отчёты по инцидентам, changelog'и — содержало буквальные `{pb['title']}`, `{severity}`, `{slug}`. Артефакт работы был мусором. |

## 3. Математика: разбор ошибок и что исправлено

Это то, что ты просил в первую очередь — чтобы ML «реально вычислял, где косяки».
Разбираю по слоям.

### 3.1. КРИТИЧНО: `fuse()` складывал приор n раз

**Было** (`detector.py`):

```python
z = Σᵢ γ^i · logit(pᵢ)
```

Это выглядит как наивный Байес, но им не является. Наивный Байес в лог-шансах:

$$\operatorname{logit} P(A \mid e_1..e_n) = \operatorname{logit}\pi + \sum_i \log \Lambda_i, \qquad \Lambda_i = \frac{P(e_i \mid A)}{P(e_i \mid \neg A)}$$

Слой отдаёт не $\Lambda_i$, а свою **апостериорную** оценку $p_i = P(A \mid e_i)$, в
которую приор уже входит. Свидетельство слоя восстанавливается вычитанием:

$$\log \Lambda_i = \operatorname{logit} p_i - \operatorname{logit}\pi$$

Старая формула этого не делала, поэтому приор входил в сумму **n раз вместо одного**.

**Почему это не абстракция.** Приор низкий (атак меньше 2% потока), значит у
большинства слоёв $p_i < 0.5$ и $\operatorname{logit} p_i < 0$. Каждый
**дополнительный** слой **тянул риск вниз**. Численно, на реальных значениях стенда:

| Что сработало | Было | Стало |
|---------------|------|-------|
| Правило 0.70 (одно) | 0.70 | 0.70 |
| Правило 0.70 + ML 0.033 | **0.30** ↓↓ | **0.81** ↑ |
| Правило 0.70 + UEBA 0.50 + ML 0.033 | **0.50** ↓ | **0.97** ↑ |
| Два правила по 0.4 | **0.35** ← меньше каждого! | **0.84** |
| Правило 0.90 + ML 0.033 | **0.62** ↓ | 0.94 |

Порог «действенного инцидента» — 0.6. То есть **подтверждение второго слоя выбрасывало
инцидент из очереди аналитика.** Эшелонированная защита работала в обратную сторону.

**Стало:**

```python
z = logit(π) + Σᵢ γ^i · (logit(pᵢ) − logit(π))
```

Свойства проверены численно (`tests/test_detector.py`):

* одиночный слой проходит **точно** без искажения: 0.42 → 0.42, 0.93 → 0.93 (приор сокращается);
* согласие не может понижать риск — **0 нарушений на 50 000 случайных наборов**;
* сигнал **ниже** приора корректно понижает риск (0.6 + 0.002 → 0.40) — это свидетельство *против*, и оно должно работать;
* ограниченность сверху сохранена.

Добавлен параметр `config.FUSION_PRIOR` (базовая частота атак). Это единственная
величина, которую надо честно оценивать по данным, а не подбирать: она равна доле
положительного класса.

**Сквозной эффект (2 сида × 14 дней, профиль stealthy, порог действия 0.6):**

| Конфигурация | PR-AUC | выигрыш над базой | Эпизодов пойм. | 95% ДИ | FP@0.6 |
|--------------|--------|--------|----------------|--------|--------|
| **logodds исправленный** | **0.2240** | **×7.2** | **74/114 = 65%** | 56–73% | 3.80% |
| max (без допущений) | 0.1733 | ×5.5 | 72/114 = 63% | 54–71% | 3.33% |
| noisy_or | 0.2097 | ×7.1 | 66/114 = 58% | 49–67% | 3.33% |
| logodds **без ML-слоя** (ablation) | 0.1627 | ×5.4 | 65/114 = 57% | 48–66% | 3.33% |

Последняя строка — ключевая для защиты: **отключение ML-слоя роняет PR-AUC с 0.224 до
0.163 и полноту с 65% до 57%.** До правок ML не мог давать вклад в принципе, и такая
ablation-таблица показала бы ноль или отрицательную величину.

### 3.2. КРИТИЧНО: калибровка Платта на сигмоиде вместо маржи

**Было:**

```python
p = sigmoid(z)              # маржа сжата в (0,1)
p = sigmoid(A·p + B)        # Платт поверх СЖАТОЙ величины
```

Обученные коэффициенты: `A = 3.852`, `B = −7.178`. Так как $p \in [0,1]$, аргумент
второй сигмоиды пробегает всего отрезок $[-7.18, -3.33]$, значит выход лежит в

$$[\sigma(-7.18),\ \sigma(-3.33)] = [0.00076,\ \mathbf{0.0347}]$$

**Модель не могла выдать больше 3.5% ни при каком событии.** Порог при этом стоял на
0.0332 — то есть в 3.5% динамического диапазона умещались и «точно норма», и «точно
атака». В сочетании с дефектом 3.1 слой был не просто бесполезен, а вреден.

**Стало** — классический Платт (1999) в редакции Lin–Lin–Weng (2007):

$$P(y=1 \mid z) = \sigma(A z + B)$$

где $z$ — **маржа** (неограниченная). Плюс три вещи, которых не было:

1. **Сглаженные цели** — чтобы $A$ не уходил в бесконечность на разделимой выборке:
   $t_+ = \frac{N_+ + 1}{N_+ + 2}$, $t_- = \frac{1}{N_- + 2}$.
2. **Метод Ньютона** с аналитическим гессианом 2×2 и отходом по шагу вместо SGD с
   фиксированными 220 эпохами и случайным перемешиванием (результат не зависит от
   порядка обхода).
3. **Отдельная выборка для калибровки** (см. 3.4).

*Побочно найдена и исправлена ошибка знака в функции потерь:* кросс-энтропия для
$P = \sigma(f)$ равна $(1-t)f + \log(1+e^{-f})$, а не $t f + \log(1+e^{-f})$.
Из-за неё линейный поиск отвергал каждый шаг Ньютона, и калибровка вырождалась в
константу ($A = 0$, весь выход = 0.98). Проверено на синтетике с известным ответом:

```
ИСТИНА:  A=+0.8000  B=-2.5000
ОЦЕНКА:  A=+0.7807  B=-2.4264      диапазон выхода [0.0000 .. 0.9991]
калибровочная кривая ложится на диагональ:  0.030→0.030  0.247→0.244  0.549→0.578  0.946→0.942
```

**Результат на боевой модели:**

| | Было (v1) | Стало (v2) |
|---|---|---|
| Диапазон выхода | 0.0008 … **0.0347** | 0.0000 … **1.0000** |
| ECE (12 бинов) | не считался | **0.0045** |
| Brier Skill Score | не считался | **+0.095** |
| Эпизодов в test | **8** | **73** |
| ДИ эпизодного recall | [31%, 86%] — бесполезен | [14%, 33%] |

Добавлено поле `format: 2` в файл модели: детектор **отказывается** загружать модель
старого формата и пишет предупреждение с командой переобучения. Молча подхватить
несовместимый файл опаснее, чем работать без слоя.

### 3.3. Brier score сам по себе бесполезен при дисбалансе

В старой версии печаталось `Brier score: 0.00309` без базы. Это выглядит блестяще, но
**константный прогноз «атак не бывает»** при доле атак $p$ даёт $\text{Brier} \approx p(1-p)$,
то есть те же ~0.003. Метрика ничего не измеряла.

Добавлены:

* **Brier Skill Score** $= 1 - \text{Brier}/\text{Brier}_{\text{base}}$ — навык
  относительно константы. BSS ≤ 0 означает «не информативнее, чем ничего».
  Текущее значение **+0.095**;
* **ECE** (Expected Calibration Error) — средневзвешенный разрыв между заявленной
  уверенностью и наблюдаемой частотой. Текущее **0.0045**;
* **база PR-AUC** = доля положительного класса, печатается рядом с PR-AUC. Сейчас
  PR-AUC 0.1923 при базе 0.0183 — **выигрыш ×11**. Без базы число 0.19 читается как
  «плохо», хотя это в 11 раз лучше случайного;
* **калибровочная кривая** прямо в выводе обучения.

### 3.4. Одна выборка использовалась трижды

Было: на `val` выбиралась сила регуляризации λ, **на ней же** обучалась калибровка,
**и на ней же** брался порог под FP-бюджет. Test был отдельный, поэтому финальные
цифры не завышались напрямую, но:

* калибровка, обученная на выборке, по которой уже выбрана модель, оптимистична;
* порог под FP-бюджет систематически занижался, и **заявленный бюджет ложных
  срабатываний был недостижим в бою** — а это то самое число, которым обосновывается
  нагрузка на аналитика.

**Стало:** хронологический сплит на **четыре** части — `train` (55%) / `val` (15%,
только выбор λ) / `calib` (15%, Платт **и** порог) / `test` (15%, ничего кроме
финальной оценки).

### 3.5. Хронологический сплит разрывал эпизоды

Комментарий утверждал, что сплит по времени защищает от утечки внутри эпизода. Это
неверно: если граница пришлась на середину кампании, её первые шаги уходят в train, а
последние — в test, и модель на тесте **узнаёт знакомую атаку**, а не обобщает.

**Стало:** `_snap_to_episode()` двигает границу вперёд до первого события, не
принадлежащего эпизоду, начавшемуся до неё.

### 3.6. Два «одинаковых» пути обучения обучали разные модели

`LogReg.fit()` при наличии numpy делал **полнобатчевый** шаг (штраф $\lambda w$ раз за
эпоху), а `_fit_python()` — **пример за примером** (штраф $n$ раз за эпоху).
Фактическая регуляризация различалась в $n \approx 20\,000$ раз, шаг обучения — во
столько же. Докстринг утверждал, что «результат обоих путей совпадает с точностью до
порядка обхода выборки». Это было не так: **подобранная по сетке λ теряла смысл на
машине без numpy.**

**Стало:** оба пути считают идентичный полнобатчевый шаг. Смещение $b$ не
регуляризуется (штраф на него сдвигал бы предсказания к 0.5 независимо от базовой
частоты класса).

### 3.7. UEBA: четыре дефекта

**(а) Порог пересчитывался на каждом событии.**
`_thr_dirty = True` ставился прямо перед вызовом `threshold_bits()`, поэтому кэш не
срабатывал ни разу — **сортировка 8 000 чисел на каждое событие потока**.
Исправлено: пересчёт не чаще чем раз в `UEBA_RECALIB_EVERY = 200` наблюдений.

**(б) Слагаемое всплеска молча выпадало.**
Условие было `if t is not None and p["rate_ewma"]:`. Значение `0.0` ложно как булево,
поэтому у актора, который в этом окне обычно **не делает ничего**, всплеск не
оценивался вовсе. А это ровно самый интересный случай: 20 действий подряд от того, у
кого базовая интенсивность нулевая.

**(в) Причина, по которой (б) не проявлялось как катастрофа — второй дефект.**
`score()` считал наблюдаемое $c$ **включая** текущее событие, а $\lambda$ копилась
**без** него. Для актора с ритмом «одно действие в 37 минут» окно в 30 минут почти
всегда пустое: $\lambda \to 0$, тогда как $c \geq 1$ всегда. Пуассоновский хвост
$P(X \geq 1 \mid \lambda \to 0) \to 0$, то есть **каждое** действие такого актора
выглядело бы бесконечно неожиданным. Один дефект прикрывал другой.
Исправлено: $c$ и $\lambda$ измеряются на одном основании, плюс нижняя граница
$\lambda \geq 1$.

**(г) Алерт «на волосок выше квантиля».**
Порог — эмпирический квантиль, у него есть собственная погрешность, а окно
интенсивности двустороннее, поэтому событие, вокруг которого поток уже прочитан
целиком, видит больше соседей, чем то же событие в момент калибровки. Разница порядка
доли бита — достаточно, чтобы рутинное действие породило алерт.
Исправлено: требуется запас `UEBA_MIN_EXCESS_BITS = 1.0` бит над порогом. Величина не
подобранная: **1 бит = ровно двукратная разница в правдоподобии.**

*Что в UEBA сделано правильно и стоит подчёркивать на защите:* круговое ядро фон Мизеса
для часа (полночь не разрыв — проверено: P(23:00) > P(01:00) > P(12:00) для ночного
актора, ядро нормировано с точностью $10^{-12}$), сглаживание Дирихле вместо бинарного
флага «раньше такого не было», порог как квантиль под бюджет тревог вместо константы,
и молчание слоя до калибровки. Пуассоновский хвост сверен с точной формулой на 5
наборах — совпадение до $10^{-9}$.

### 3.8. ML-слой теперь участвует в решении двумя способами

Раньше модель влияла на решение **только** когда сама превышала порог FP-бюджета —
то есть в 0.05% случаев, там где и без неё справлялись. Добавлен канал
**свидетельства**: если $p$ заметно выше приора, но ниже порога, слой не создаёт
тревогу (не будит человека), но добавляет положительный вклад в слияние, когда
сработал другой слой. В логарифме шансов вклад равен $\log\frac{p(1-\pi)}{\pi(1-p)}$
и при $p > \pi$ положителен.

Это и есть эшелонирование: **слой добавляет уверенности, а не тревог.** Раньше это было
заявлено в комментарии к `ML_RISK_CAP`, но не реализовано.

### 3.9. Объяснимость: `explain()`

Добавлен метод `MLScorer.explain()`, отдающий полное аддитивное разложение маржи:

```json
{"bias": -2.27, "margin": 4.81, "proba": 0.87,
 "top": [{"feature": "burst_delete", "value": 0.92, "contribution": 1.43},
         {"feature": "path_secretdir", "value": 1.0, "contribution": 0.71}, ...]}
```

Для линейной модели $w_j z_j$ — **точное** разложение скора (совпадает со

## 4. Метрики и методология оценки

### 4.1. `metrics.py` прогонял детектор по потоку ДВАЖДЫ

Детектор потоковый и **с состоянием**: `Enricher` копит оконную историю актора, `UEBA`
— профили и резервуар для квантиля. `compute()` проходил по событиям дважды (второй
раз ради PR-AUC), причём тем же синглтоном `run_defense._ENGINE`.

На втором проходе профили были «прогреты» всей выборкой, порог UEBA стоял на другом
значении, история каждого актора удваивалась. **PR-AUC считался по риску, который
никогда не выставлялся в бою**, и в отчёте соседствовали две несогласованные цифры по
одному прогону.

Исправлено: единственный проход, риски запоминаются.

### 4.2. Detection rate завышался случайными совпадениями

Эпизод считался обнаруженным, если **любой** алерт того же актора попал в окно эпизода
— включая алерт на его соседнее **доброкачественное** действие. Атакующий в рабочее
время делает и обычную работу, поэтому совпадения не редкость.

Исправлено: строгий критерий — алерт **на событии этого эпизода** (по `episode_id`).
Мягкий критерий тоже считается и печатается: **разница между ними и есть величина
накрутки.** Это честнее, чем просто заменить одно на другое.

### 4.3. MTTD — цензурированная выборка без предупреждения

Среднее считалось **только по пойманным** эпизодам: у непойманных времени обнаружения
не существует. Число подавалось как «MTTD», а не «MTTD среди пойманных». Классическая
survivorship bias, и рецензент за неё зацепится.

Исправлено: печатается среднее, **медиана**, и явно — по скольким эпизодам из скольких
посчитано.

### 4.4. Alerts/day имел обратный знак ошибки

```python
span_days = (max(alert_times) - min(alert_times)) / 86400   # ← разброс АЛЕРТОВ
per_day = len(alerts) / span_days
```

Знаменатель — разброс времён самих алертов, а не длительность прогона. Если все алерты
пришлись на один час двухнедельного прогона, метрика выдавала «240 алертов в день»
вместо честных 0.7. **Чем тише детектор, тем сильнее завышался показатель его
шумности.**

Исправлено: знаменатель — длительность всего потока.

### 4.5. FP-rate «по действенным инцидентам»

Знаменатель — только инциденты с `max_risk ≥ 0.6` **или** подкреплённые правилом.
Обоснование в комментарии есть и оно небезосновательно, но выбор порога отсечения
влияет на итоговую цифру, а альтернатива не показана. Рецензент справедливо спросит,
почему 0.6.

**Рекомендация** (не сделано): печатать FP по трём знаменателям — все сырые детекты /
все инциденты / действенные инциденты — и объяснить разницу. Это сильнее, чем выбрать
удобный.

### 4.6. Правило, которое физически не могло сработать

`detections/perm-discovery.json` требует `burst_api_read_15m >= 5`, а шаг атаки
`_a_perm_discovery` выдавал **ровно 4** запроса. Техника **T1069 числилась покрытой
правилом, которое не срабатывало ни на одном прогоне.** Именно так и создаётся ложное
покрытие ATT&CK.

Исправлено: шаг выдаёт 5–8 запросов. `tests/test_rule_coverage.py` теперь зелёный —
39/39 правил срабатывают, покрытие 33/46 техник (72%), 13 честно объявленных слепых зон.

### 4.7. Что в статистике сделано правильно

`stats.py` — сильный модуль, ошибок не найдено. Сверено с аналитикой:

| Проверка | Результат |
|----------|-----------|
| Уилсон 41/55 | [0.617, 0.842] ✅ |
| ROC-AUC идеального разделения | 1.0 ✅ |
| ROC-AUC при полном совпадении (связки) | 0.5 ✅ |
| PR-AUC идеального разделения | 1.0 ✅ |

группой. Поправка Холма реализована корректно.

### Задача 2 — ablation со значимостью ✅ + два серьёзных открытия

`research/ablation.py`: одна нагрузка, четыре конфигурации, парный Макнемар,
поправка Холма, bootstrap-интервалы PR-AUC.

**Открытие 1: поведенческий слой работал ХУЖЕ СЛУЧАЙНОГО.** Замер компонент
(`tools/ueba_components.py`, 20 329 событий):

| компонента | ROC-AUC | вывод |
|---|---|---|
| hour | 0.577 | несёт сигнал |
| action | 0.494 | не различает |
| repo | 0.492 | не различает |
| burst | **0.400** | **работает против** |
| **сумма всех четырёх** | **0.455** | **хуже случайного** |

Причины — не статистические, а конструктивные, и выводятся из постановки:

* `action` не различает **по построению**: `taxonomy.py` специально уравнивает
  действия атаки и нормы. ROC 0.494 — это подтверждение того, что нормализация
  словаря сработала, а не дефект;
* `burst` работает против, потому что профили уклонения **растягивают** шаги
  кампании: атакующий тише обычной работы. Плюс поток пачечный (Var/E ≈ 3.0), и
  пуассоновский хвост при сверхдисперсии оценивает обычную пачку из 20 событий в
  27.8 бит при эмпирических 8.4 — то есть добавляет НОРМЕ +19 бит шума.

Корень — методологический: **неожиданность −log P(x|норма) является мерой улики
только при равномерной альтернативе.** Для `burst` это допущение нарушено, и знак
вклада переворачивается. Слой переведён на компоненты, для которых допущение
защитимо (`repo` + `hour`); интенсивность осталась признаком слоя L2, где знак
выучивается по данным — и модель самостоятельно дала `burst_any` вес −1.15,
то есть выучила ровно то, что здесь выведено из постановки.

**Открытие 2: слияние было только пособытийным.** Многошаговая кампания
растянута по событиям: правило срабатывает на шаге «push секрета», поведенческий
слой — на «ночном доступе», модель — на «выгрузке». Пособытийное слияние эти
свидетельства **никогда не встретит**, а `max_risk` не умеет складывать. Вклад
слоя выходил статистически неотличимым от нуля не потому, что слой слеп, а
потому, что его свидетельство некуда было положить.

Добавлено слияние **на уровне инцидента** (`Correlator._incident_risk`): максимум
по каждому слою отдельно, затем та же формула. Проверка: правило 0.5 на шаге 1 +
UEBA 0.3 на шаге 3 дают инцидент 0.87 вместо прежних 0.5 — то есть выше порога
действия вместо ниже.

Побочно найдено: свидетельство ML не попадало в инцидент, из-за чего инцидентная
полнота оказывалась НИЖЕ пособытийной — величина, которая по построению не может
быть отрицательной. Исправлено.

**Итог ablation** (2 сида × 14 дней, 228 эпизодов, порог 0.6):

| конфигурация | PR-AUC | эпизодный recall | значимость vs full |
|---|---|---|---|
| full | 0.251 [0.220–0.288] | 184/228 = **81%** | — |
| no_ml | 0.206 | 169/228 = 74% | p = 0.001 **значимо** |
| no_ueba | 0.261 | 180/228 = 79% | p = 0.50 не значимо |
| rules_only | 0.215 | 167/228 = 73% | p = 0.0001 **значимо** |

Честный вывод: **полный стек значимо полнее одних сигнатур (+7 п.п.), вклад слоя
ML значим, вклад поведенческого слоя на этом объёме — нет.** Скрипт сам печатает,
что отсутствие значимости не является доказательством отсутствия эффекта.

### Задача 6 — калибровки сравниваются замером ✅

В `stats.py` добавлена изотоническая регрессия (PAVA, ~40 строк без
зависимостей). Проверена на связи `P(y|s) = s²`, которую сигмоида не может
выучить в принципе: восстанавливает с максимальной ошибкой 0.033, монотонна,
на антимонотонных метках корректно вырождается в константу.

Ключевое уточнение методики. Наивный критерий «минимальный ECE» выбрал бы
изотонику всегда, но она **разрушает ранжирование**: её плоские участки склеивают
разные маржи в одну вероятность, а очередь аналитика отсортирована по риску.

Правильная формулировка: **любое строго монотонное преобразование сохраняет
PR-AUC ТОЧНО** (обе метрики зависят только от порядка). Значит колонка PR-AUC
измеряет не качество модели, а сколько разрешающей способности разрушила
калибровка. Замер подтвердил теорию до четвёртого знака:

| калибровка | ECE | PR-AUC | потеря ранга |
|---|---|---|---|
| Платт | 0.00319 | 0.2046 | **ровно 0.0%** |
| изотоника | 0.00185 | 0.1925 | 5.9% |

Критерий: минимальный ECE **среди тех, что теряют не более 5% ранга**. На текущих
данных побеждает Платт. Детектор умеет применять обе.

Между 0.20 и 0.80 — плато: полнота не меняется, нагрузка отличается в 1.6 раза.
Подъём порога до 0.80 снимает **34% очереди** и добавляет 7 п.п. точности

## 14. Прогон на живой машине: что нашлось после

Проверка на реальной среде (Windows, Python 3.12, живой GitLab v19.0.1, Ollama)
дала три провала. **Два из них — мои**, и они одного класса.

### Мои дефекты: платформозависимость в тесте платформонезависимости

`tests/test_generated_content.py` сравнивал пути через `p.startswith("./tests/")`.
На Windows `os.walk` отдаёт `.\tests\...`, и **все такие проверки молча
перестали срабатывать**:

* тест не смог исключить сам `ml_features.py` → посчитал его «второй копией
  словаря действий»;
* тест не смог исключить каталог `tests/` → насчитал лишние 20 молчаливых
  `except`, и бюджет 105 превратился в 123.

Ирония в том, что проверка платформонезависимости сама оказалась
платформозависимой, а симптом коварен: на Linux всё зелено, на Windows два
ложных провала, и непонятно, сломан продукт или тест.

Исправлено: `_py_files()` нормализует разделитель, добавлен
`test_paths_platform_independent`. Проверено узкой имитацией Windows (подмена
`os.walk`/`os.sep` без вмешательства в импорт): **0 провалов**.

Заодно просканировал всю кодовую базу на этот класс — построения путей
конкатенацией нет ни одного, остальные posix-сравнения относятся к URL, а не к
файловой системе.

### Бюджет молчаливых `except` пересчитан честно

Из 105 обработчиков **23** оказались идиомой `sys.stdout.reconfigure(encoding=...)`
— она нужна для совместимости, логировать её нечем (логгер в этот момент ещё не
настроен), и считать её техдолгом значит размывать оставшиеся. Исключены из
подсчёта явно, потолок опущен **105 → 82**, фактически **80**.

### `/api/report/full.pdf` → 503: это не поломка

Маршрут отдаёт 503 с текстом «PDF-модуль не установлен, выполни
`pip install reportlab`» — то есть делает ровно то, что должен. Смоук-тест
считал провалом любой 5xx.

Теперь тест отличает **объяснённый отказ необязательной возможности** (503 +
внятная причина в теле) от настоящей поломки (500 или 5xx без объяснения).
Первое не проваливает прогон, но печатается отдельной строкой — «просто зелено»
тоже неверно. Проверено имитацией отсутствия `reportlab`.

### Доля ложных: три знаменателя вместо одного

Это был пункт №1 из «осталось», и твой прогон показал его наглядно: **60.7%**.
Одной честной цифры здесь не существует, потому что «ложная тревога» значит
разное на разных уровнях конвейера. Теперь печатаются все три плюс зависимость
от порога:

```
по событиям:      78.1%  (164/210 сырых детектов на норме)
по инцидентам:    72.1%  (31/43 после корреляции)
по ДЕЙСТВЕННЫМ:   60.7%  (17/28 дошли бы до аналитика)

risk >= 0.2: 67.6%   risk >= 0.6: 60.7%   risk >= 0.9: 54.5%
```

И главное — **что эта цифра значит при таком дисбалансе**. Атаки составляют
0.42% потока: случайно взятый инцидент верен в 0.42% случаев, а действенный —
в 39%. Это **выигрыш в 94 раза**. При 2.5 алертах в симулированный день
разобрать три инцидента, из которых один настоящий, — рабочая нагрузка.
Для SOC решает не доля, а абсолютное число тревог.

### Что подтвердилось на живых данных
