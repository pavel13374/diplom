# SOC Simulator — разбор и роадмап (реализм + подготовка к ML)

Аудит текущего кода: `config.py`, `events.py`, `activities/anomaly.py`, датасет
`data/events.jsonl` (3231 событий, ~4.8% аномалий). Ниже — что улучшить, чтобы
выглядело как настоящая симуляция, и что доделать в слое данных под ML
(UEBA, secret detection и не только).

---

## 0. Что уже сделано хорошо (не трогать)

- Жизненный цикл правил со статусами/возрастом/FP-историей — это и есть «душа» реализма.
- Размеченный журнал с временными признаками из **sim-времени**, а не из реального.
- Benign-lookalikes (`.env.example`, фейковые фикстуры, base64) с `is_anomaly=false` —
  это редкая и очень правильная вещь, большинство учебных датасетов её не имеют.
- Декларативная модель «опасных» аномалий (коммит в policy-файл вместо реального
  admin-API) — безопасно и при этом размечается.

---

## 1. Критичное — сделать ДО защиты

### 1.1. Секреты в `config.py` (иронично для SOC-проекта)
`ADMIN_TOKEN`, `TELEGRAM.token`, `WEB_ADMIN_PASS = "123"` лежат прямо в репозитории.
Любой ревьюер диплома это заметит первым.
- Вынести в `.env` + `os.getenv(...)`, добавить `.env.example` с плейсхолдерами.
- `.gitignore` → `.env`, `web_config.json`, `.sim_state.json`, `data/events.jsonl`, `logs/`.
- **Отозвать** засвеченный GitLab-токен и Telegram-токен (они уже скомпрометированы).

### 1.2. Утечка метки (label leakage) — ломает любой ML
В `events.jsonl` каждый инцидент дублируется служебным событием
`action="anomaly"`, `message="injected anomaly: ..."`, плюс поля `anomaly_subtype`,
`executed`. Модель на этом получит 100% accuracy тривиально и обучится мусору.
- Эти служебные `action="anomaly"` записи — **только для алертов/телеметрии**, в
  обучающую выборку их нельзя. Помечай их отдельным полем `meta=true` и фильтруй.
- При выгрузке датасета drop-лист колонок: `anomaly_type`, `severity`, `is_anomaly`
  (это таргеты, не фичи), `anomaly_subtype`, `executed`, `detail`, `message`
  (в message часто прямым текстом «Мержу без ревью, срочно» — тоже лик).
- Сделай скрипт `export_dataset.py`, который чистит лик и режет на train/val/test
  **по времени** (не случайно), чтобы не было утечки будущего в прошлое.

### 1.3. Тривиально разделимые классы
55 из 156 аномалий — `merge_without_review`, 40 — `self_approval_merge`. Их сигнал
буквально «approver == author» или «нет approve перед merge» — это **правило, а не
ML**. Если оставить так, классификатор выучит одно булево поле.
- Балансируй веса: сейчас self/merge-without-review суммарно доминируют в позитивном
  классе. Подними долю «тонких» (secret_*, exfil, pipeline) или режь частые.
- Для честной демонстрации ML держи рядом **rule-based baseline** (эти простые
  случаи ловятся правилами) и показывай, что ML добавляет на «тонких».

## 2. Реализм и «красота» симуляции

### 2.1. Несоответствие времени
`ts_sim` (нарратив) и `ts_real` отличаются на часы, а коммиты в GitLab штампуются
реальным временем. На демо «журнал рабочего дня» и история GitLab разъедутся.
- Везде в UI/логах опирайся на `ts_sim` (уже так).
- Подумай о `GITLAB_DATES="sim"` для коммитов через `--date`, если нужен красивый
  GitLab-граф по нарративному времени.

### 2.2. Слишком высокая доля аномалий
`ANOMALY_RATE_OFFHOURS = 0.30` → каждое третье ночное действие = атака. В реальном
SOC это <<1%. Сейчас удобно для генерации позитивов, но неправдоподобно.
- Введи два профиля в конфиге: **`realistic`** (rate ~0.005–0.02, для «как настоящее»)
  и **`training`** (текущие высокие, чтобы быстро набрать позитивов). Документируй,
  что для отчёта по реализму берётся первый, для обучения — второй.

### 2.3. Полнота схемы событий
Часть событий без `project`/`path` (например `action="activity"`). Для красоты ленты
и для фич приведи схему к единому виду — у каждого события минимум actor/role/action/
project/ts. Добавь `session_id` (см. 3.2).

### 2.4. Визуальная часть веб-панели (для защиты — сильно усиливает «вау»)
- **Heatmap активности** по часам×дням недели (видно рабочий ритм и ночные всплески).
- **Таймлайн аномалий** с цветом по severity.
- Мини-граф «кто-в-какой-репозиторий» (actor↔repo) — основа для UEBA-нарратива.
- Простые счётчики precision/recall, когда подключишь детектор.

### 2.5. Мелочи правдоподобия
- Добавь редкие «человеческие» паузы между сессиями, обед уже есть — хорошо.
- Реверты/инциденты ночью — уже есть, это правильный сигнал.

## 3. Подготовка слоя данных к ML (главное)

Сейчас событие — атомарное действие. Для ML нужно три вещи: **(а)** богаче признаки
на событие, **(б)** агрегации/сессии, **(в)** сущностные профили (entities). Ниже —
что конкретно дописать в `events.emit(...)`.

### 3.1. Обогатить признаки события
Добавляй в `extra=` при пуше/диффе:
- `files_changed`, `lines_added`, `lines_deleted`, `bytes` (часть уже есть — сделать везде).
- `path_ext`, флаги пути: `is_ci` (`.gitlab-ci.yml`), `is_env` (`.env`),
  `is_secrets_repo`, `is_protected_branch`.
- `max_token_entropy`, `has_secret_regex` (см. раздел 5) — даже для нормальных пушей,
  чтобы это были честные признаки, а не разметка.

### 3.2. Сессии и последовательности
Логический поток `branch_create → push → mr_open → approve → merge` — это одна сессия.
- Добавь `session_id` (uuid на флоу) и `step_idx`. Тогда возможны **sequence-модели**
  и фичи «сколько шагов от ветки до merge», «был ли approve между push и merge».
- Это же даёт честный сигнал для `self_approval`/`merge_without_review` как
  последовательности, а не одного поля.

### 3.3. Сущностные профили (фундамент UEBA)
Заведи выгрузку агрегатов по `actor` (и по `actor×repo`) в скользящих окнах
(час / день / 7 дней): количество действий, доля ночных, набор репозиториев,
типичный action-mix, средний размер диффа. Это «baseline», от которого UEBA
считает отклонение.

### 3.4. Скрипт выгрузки
`export_dataset.py`: читает `events.jsonl` → чистит лик (раздел 1.2) →
строит фичи (3.1–3.3) → отдаёт `dataset.parquet` + `labels`. Сплит по времени.

## 4. UEBA (User & Entity Behavior Analytics)

UEBA = «насколько действие необычно **для этого пользователя / его пиров**».
Не «секрет в коммите», а «Мария впервые за ночь пушит в soc-secrets, чего раньше
никогда не делала». Что нужно от симулятора:

### 4.1. Каких данных не хватает — добавить как события
- **Аутентификация**: `login`, `logout`, `failed_login`. Это классика UEBA
  (брутфорс, off-hours login, impossible travel). Сейчас их вообще нет.
- **`source_ip` / `geo` / `device`** на действиях — синтетические, но позволяют
  фичи «новый IP», «новая страна», «невозможное перемещение».
- **Объёмные действия**: клонирование/выгрузка большого числа файлов, скачивание
  артефактов — сигнал эксфильтрации (частично есть: `mass_deletion`, `data_exfiltration`).

### 4.2. Признаки UEBA, которые будешь считать
- Отклонение от **личного** baseline: z-score по частоте действий, новизна репозитория/
  ветки/времени для этого актора (`is_first_time_repo`, `is_unusual_hour_for_actor`).
- Отклонение от **пиров** (peer-group): инженеры vs lead vs bot — у каждого свой
  нормальный профиль; действие «как у другой роли» подозрительно.
- **Velocity**: всплеск числа действий в окне (15 мин / 1 ч).
- **Graph/affinity**: пара actor↔repo, которой раньше не было.

### 4.3. Модели
- Старт без меток: `IsolationForest` / `LocalOutlierFactor` на агрегатах по актору.
- Полу-supervised: автоэнкодер на «нормальных» сессиях, аномалия = высокая ошибка
  реконструкции.
- Метрика: precision@k, PR-AUC (не accuracy — класс редкий).

## 5. Detection секретов

У тебя инжектятся секреты и есть lookalikes — отличная база. Но **в `events.jsonl`
самого секрета/его признаков нет**, только метка `secret_type`. На одном журнале
secret-детектор не обучить. Нужен слой признаков контента.

### 5.1. Добавить признаки контента (для ВСЕХ пушей, не только аномалий)
В `agents/base.py:push_file` посчитай по содержимому и положи в событие:
- `shannon_entropy` (макс по токенам) — высокий у настоящих ключей, низкий у плейсхолдеров.
- `has_high_entropy_token` (порог энтропии + длина).
- `regex_hits`: совпадения с известными паттернами — `glpat-`, `AKIA[0-9A-Z]{16}`,
  `-----BEGIN ... PRIVATE KEY-----`, `xox[baprs]-`, `eyJ...` (JWT), `ghp_`, и т.д.
- `filename_signal`: `.env`, `secrets`, `credentials`, `id_rsa`.
- `placeholder_signal`: `EXAMPLE`, `CHANGEME`, `xxx`, `<...>`, `dummy`, `test`.

Тогда задача честная: lookalike (`.env.example` с `placeholder_signal=1`,
низкая энтропия) vs реальная утечка (высокая энтропия + regex + `.env`).

### 5.2. Что показать
- Baseline-детектор на регулярках (как gitleaks/trufflehog) + ML поверх энтропии и
  контекста (путь, ветка, кто, время) — ML снижает FP на lookalikes.
- Метрики на твоём размеченном наборе (точность именно на hard-negatives).

### 5.3. Расширить банк
- Больше типов в `secrets_bank.py`: AWS, GCP service-account JSON, JWT, SSH private
  key, `.pem`, DB connection string, Slack/Telegram токены.
- Больше lookalikes: документация с примером ключа, тестовый vault с фейками,
  зашифрованные (а не plaintext) секреты.

## 6. Что ещё, кроме UEBA и секретов (направления детекта)

Твои аномалии уже покрывают это — стоит оформить как **отдельные ML-задачи**:

1. **Insider threat / эксфильтрация** — объёмные признаки: размер коммита, base64-блобы,
   `mass_deletion`, `data_exfiltration`. Детект по аномальному объёму.
2. **Контроль доступа / privilege escalation** — `weaken_protection`,
   `grant_secret_access`, `rogue_token`, `direct_push_protected`. Граф прав + правила.
3. **CI/CD supply chain** — `disable_pipeline_security`, `pipeline_token_leak`,
   `artifact_secret_exposure`. Анализ диффов `.gitlab-ci.yml`.
4. **Process anomaly (обход ревью)** — `self_approval`, `merge_without_review` как
   нарушение последовательности (sequence-модель из 3.2).
5. **Time-series аномалии объёма активности** — всплески по часам (heatmap из 2.4).
6. **Graph anomaly** — необычные рёбра actor↔repo / approver↔author.

Для диплома достаточно сделать сильно **2–3** из них (UEBA + secrets + одно из выше),
а остальные описать как «расширяемость».

## 7. Приоритеты (порядок действий)

1. **Безопасность + анти-лик** (раздел 1) — без этого ML и защита проседают.
2. **`export_dataset.py`**: чистка лика, фичи событий, сплит по времени (1.2, 3.4).
3. **Признаки контента для секретов** в `push_file` (5.1) — открывает secret-детектор.
4. **Аутентификация + source_ip/geo события** (4.1) — открывает UEBA.
5. **session_id + агрегаты по актору** (3.2, 3.3).
6. **Два профиля частоты** realistic/training + ребаланс аномалий (1.3, 2.2).
7. **Визуализация**: heatmap, таймлайн аномалий, метрики детектора (2.4).
8. Обучить и показать: rule-based baseline → UEBA (IsolationForest/AE) →
   secret-классификатор, метрики PR-AUC / precision@k.
