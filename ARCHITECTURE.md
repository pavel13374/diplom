# Архитектура Sentinel

Документ для того, кто открыл репозиторий впервые и хочет понять, как всё
устроено, за пятнадцать минут. Пользовательское описание — в `README.md`,
каталог правил — в `detections/_index.md`.

---

## 1. Один вопрос, на который отвечает стенд

> Можно ли обнаружить злоумышленника внутри процесса разработки, видя только
> обычный аудит-лог GitLab — коммиты, merge request'ы, CI, токены, права — и
> **не имея разметки** о том, где атака?

Всё остальное в проекте существует ради того, чтобы ответ на этот вопрос был
измеримым и честным.

```
 ┌──────────────────────────┐   ┌──────────────┐   ┌───────────────────────────┐
 │ scheduler                │   │ eventstore   │   │ run_defense (курсор)      │
 │  ├─ agents/     люди     │──▶│ SQLite + WAL │──▶│  └─ observed()  анти-лик  │
 │  ├─ activities/ работа   │   │ курсоры      │   │        ↓                  │
 │  └─ red_team    атаки    │   │ очередь      │   │ detector                  │
 │                          │   │  команд      │   │  ├─ Enricher   окна       │
 │ content/  банки текстов  │   └──────────────┘   │  ├─ L0 правила            │
 │ gitlab_client  REST API  │          ▲           │  ├─ L1 UEBA (биты)        │
 └──────────────────────────┘          │           │  ├─ L2 ML                 │
                                       │           │  └─ fuse()  лог-шансы     │
                                       │           │        ↓                  │
                                 команда «запусти  │ correlator → инциденты    │
                                  кампанию»        │        ↓                  │
                                       └───────────│ llm_client  триаж         │
                                                   └───────────────────────────┘
```

Две половины **не знают друг о друге**. Единственный канал — журнал событий, и
он физически содержит только наблюдаемые поля. Это не украшение: если бы
детектор имел доступ к внутренним структурам мира, он мог бы подглядеть
разметку, и метрики потеряли бы смысл.

Обратный канал ровно один — очередь команд в том же журнале: кнопка «запустить
кампанию» на консоли защиты ставит команду, мир её забирает и исполняет.

## 3. Принцип честности

Разметка (`is_anomaly`, `episode_id`, `technique_id`, `campaign_id`) живёт в
слое мира и используется **только постфактум**, когда считаются метрики.
Защита её не видит: `run_defense.observed()` срезает эти поля перед подачей в
детектор.

Но одного вырезания полей мало, и это главный урок проекта.

**Утечка через словарь действий.** Пока каждый шаг атаки эмитил собственное
действие (`steal_oauth`, `repo_enum`, `mass_delete`), правило вида
`{"action": "steal_oauth"}` не обнаруживало атаку — оно читало метку под другим
именем, потому что такого действия у обычных сотрудников не бывало ни разу.

Решение — `taxonomy.py`: закрытый словарь действий, которые видны в настоящем
аудит-логе GitLab. И работа, и атака описываются одними и теми же действиями,
различаясь только **атрибутами**:

| Шаг атаки | Наблюдаемое действие | Что отличает от нормы |
|---|---|---|
| кража OAuth-токена | `api_read` | `api_path=/oauth/tokens` |
| разведка | `api_read` × N | объём выдачи и охват репозиториев |
| массовое удаление | `file_delete` × N | всплеск в окне (вычисляется) |
| лишний токен | `token_create` | scope `api`, не себе, без срока |
| канал управления | `hook_create` | хост вне периметра |
| заметание следов | `force_push` | защищённая ветка + потерянные коммиты |

Проверяется двумя тестами:

```
python tests/test_antileak.py   # защита не видит ПОЛЕЙ разметки мира
python tests/test_leakage.py    # ни одно ЗНАЧЕНИЕ признака не определяет метку
```

## 4. Слои детектирования

Всё в `detector.py`. Событие проходит их по очереди.

### E — Enricher

Скользящие оконные агрегаты по актору: `burst_file_delete_10m`,
`burst_api_read_15m`, `api_items_sum_15m`, `distinct_projects_1h` и другие.

Нужен именно потому, что словарь действий нормализован: массовое удаление
выглядит как N обычных `file_delete`, и «массовость» приходится **вычислять**,
а не читать из имени события.

### L0 — правила (Detection-as-Code)

41 правило в `detections/*.json`, декларативные, подхватываются без перезапуска
логики. Каждое ссылается на технику MITRE ATT&CK и содержит поле `rationale` —
почему оно срабатывает и почему не ловит норму.

Каждое правило **проверяется по схеме при загрузке**: обязательные `id`,
`title`, непустой `when`; операторы только из поддерживаемого набора; `risk`
внутри `[0,1]`; `severity` из перечисления. Раньше проверялся только уникальный
`id`, и это стоило дважды: правило без `title` роняло `KeyError` на КАЖДОМ
подходящем событии (цикл ингеста считал это ошибкой события и шёл дальше — то
есть консоль молча переставала выдавать тревоги), а опечатка в операторе
(`gte` вместо `>=`) делала правило вечно молчащим, при этом оно оставалось в
каталоге и считалось в покрытии. Отвергнутые правила теперь названы в логе и
видны в `/api/detections` — отсутствовать молча они не могут.

Проверяется `tools/lint_rules.py` и `tests/test_rule_coverage.py`
(каждое правило обязано хоть раз сработать на корпусе — иначе это мёртвый код,
создающий видимость покрытия).

### L1 — UEBA, вероятностный

Скор события — суммарная **неожиданность в битах**:

```
S(e) = −log₂P(repo|actor) − log₂P(action|actor)
       − log₂P(hour|actor) − log₂P(всплеск ≥ наблюдаемого)
```

| Компонента | Модель |
|---|---|
| репозиторий, действие | мультиномиальное распределение со сглаживанием Дирихле |
| час активности | круговой KDE с ядром фон Мизеса (час — циклическая величина) |
| всплеск | хвостовая вероятность Пуассона относительно личной интенсивности (EWMA) |

Слагаемые сопоставимы между собой и складываются корректно. Порог — **квантиль
эмпирического распределения** под заданный бюджет тревог (`UEBA_ALERT_BUDGET`),
а не константа. До накопления статистики слой молчит.

### L2 — ML

Логистическая регрессия по 87 наблюдаемым признакам (`ml_features.py`) с
калибровкой Платта. Модель — `models/runtime_model.json`, воспроизводится
скриптом `research/train_runtime_model.py`. Без файла модели слой молча
выключается.

Линейная модель выбрана осознанно: вклад каждого признака виден, и алерт можно
объяснить аналитику. Для SOC объяснимость важнее лишней доли AUC.

### Слияние

`fuse()` — сумма лог-шансов с затуханием γ^i. Не noisy-OR: он корректен только
при условной независимости, а три слоя смотрят на одно событие и срабатывают
по коррелирующим причинам.

### Устойчивость к уклонению

Признаки содержимого считаются дважды: по исходному тексту и по
**нормализованному**. Нормализация снимает склейку строковых литералов
(`"glpat-" + "Ab3x…"`), перенос обратным слэшем, `\xNN`/`\uNNNN`/`%NN`-escape,
символы нулевой ширины, кириллические двойники латиницы и раскрывает base64.
Результаты объединяются, а факт «сигнатура проявилась только после
нормализации» становится отдельной уликой (`evasion_signal`).

Это не запас прочности, а закрытие измеренной дыры: до нормализации выражение
`"glpat-" + "Ab3xK9mQ7zR2pL5wT8vN"` давало энтропию 0.00 и ноль сигнатур, то
есть склейка строк отключала СРАЗУ ОБА слоя — сигнатурный и энтропийный.

Заглушечность определяется **по каждому совпадению**, а не по файлу: раньше
одно слово `TODO` где угодно в содержимом роняло риск настоящего токена с 0.92
до 0.00, потому что четыре правила требуют `placeholder_signal: false`.

Объём разбора ограничен (`MAX_ANALYZE_BYTES`): файл больше лимита смотрится по
голове и хвосту, помечается `truncated`, и об этом сообщает отдельное правило.
Размер файла выбирает автор коммита, а разбор синхронен внутри конвейера.

Базовая линия слоя L1 **не учится на собственных тревогах**: наблюдение, на
котором сработало правило, в профиль не идёт, а счётчики профиля стареют.
Иначе достаточно подготовить двести безобидных ночных обращений, чтобы обе
входящие в скор компоненты (`repo`, `hour`) сошлись к нулю бит.

### Подавление и корреляция

`Suppressor` гасит повтор `(actor, rule)` в окне — иначе одна уборка на 12
файлов даёт 8 тревог вместо одной. `correlator.py` склеивает алерты одного
актора во времени в инцидент с цепочкой ATT&CK.

Уровень инцидента выводится **из порога действия** (`ACTION_THRESHOLD`), а не
назначен отдельными константами: «high и выше» означает ровно «дошло до
очереди». Раньше инцидент с риском 0.65 показывался как HIGH и при этом в
очередь не попадал.

Границы роста заданы явно (`MAX_INCIDENTS`, `MAX_ALERTS_PER_INCIDENT`,
`MAX_CHAIN`), а цепочка поддерживается отсортированной вставкой. Затопление
тревогами — доступное атакующему действие: без границ инцидент из n сработок
стоил O(n² log n), а словарь инцидентов не чистился никогда.

Приглушение шумного правила по вердиктам аналитика **понижает, а не удаляет**
сработку, не применяется к правилам уровня `critical` и к правилам с
`risk >= 0.8`, и учитывает только свежие вердикты. Прежний вариант был
выключателем детектирования, доступным через обычный шум: три отметки
«ложное» — и правило не срабатывает больше никогда, для всех акторов, молча.

## 6. Что запускать

```
python tools/doctor.py                   # диагностика окружения и слоёв
python tools/lint_rules.py               # статическая проверка правил
python tools/rule_quality.py             # точность каждого правила
python tools/gen_rule_index.py           # пересобрать detections/_index.md

python research/train_runtime_model.py   # обучить модель слоя L2
python research/experiments.py           # ablation: слои × уклонение, со значимостью
python research/experiments_holdout.py   # regex против ML на невиданном формате
python research/experiments_roc.py       # одиночный признак против слияния
python metrics.py                        # метрики по накопленному журналу
```

## 7. Границы применимости

Стенд синтетический. Сотрудники, репозитории, секреты и атаки придуманы;
секреты в коммитах — фальшивые строки, похожие по форме на настоящие токены.

Из этого следует главное ограничение: **распределения нормального поведения
задаёт генератор, а не реальная команда**. Метрики честны относительно этого
генератора и характеризуют методику, а не абсолютное качество детектора в
production. Именно поэтому в работе так много внимания уделено тому, чтобы фон
не был вырожденным: в нём есть benign-двойники секретов, рабочие сессии,
массовые уборки репозитория, ночные сборки и админ-операции — всё то, что в
реальности создаёт ложные срабатывания.

Техники ATT&CK, принципиально ненаблюдаемые в этом контуре (фишинг, эндпоинт,
сетевой уровень), в модель угроз не включены: их отсутствие — граница системы,
а не пробел в правилах.
