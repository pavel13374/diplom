## Главное в одном абзаце

Работа проверяет, можно ли обнаружить злоумышленника внутри процесса разработки
по обычному аудит-логу GitLab, не имея разметки. Ревью показало, что
измерительная часть — то, ради чего стенд и делался — давала результат, который
сам себя опровергал: половина правил читала метку под другим именем, главное
правило по разрушительным действиям было сломано, глава экспериментов не
запускалась, а математики в поведенческом слое не было вовсе. Всё перечисленное
устранено, и каждый дефект превращён в содержательный раздел работы.

## 1. Пробой анти-лика: правила читали метку

**Было.** Каждый шаг атаки эмитил собственное «говорящее» действие: `steal_oauth`,
`repo_enum`, `perm_discovery`, `mass_delete`, `exfil_altproto` и ещё десяток.
Ни одно из них не встречалось у обычных сотрудников **ни разу**. При этом
**19 из 38 правил** состояли ровно из одного условия:

```json
{ "when": { "action": "steal_oauth" } }
```

Формально анти-лик проходил: поля `is_anomaly`, `episode_id`, `technique_id`
честно вырезались. Фактически знание «action == steal_oauth» полностью
эквивалентно знанию «это атака». Такое правило не обнаруживает — оно читает
ответ под другим именем, и все метрики на нём ничего не значат.

**Стало.**

- `taxonomy.py` — закрытый словарь действий, которые реально видны в аудит-логе
  GitLab. И обычная работа, и атака описываются **одними и теми же** действиями,
  различаясь только наблюдаемыми атрибутами.
- `activities/anomaly.py` переписан: «кража OAuth-токена» — это теперь
  `api_read(api_path="/oauth/tokens")`, массовое удаление — N обычных
  `file_delete`, разведка — серия `api_read` с большой выдачей.
- `activities/ops_admin.py` — обычная команда тоже создаёт токены, добавляет
  deploy-ключи и вебхуки, заводит ночные расписания, меняет права участникам,
  делает force-push после rebase. Без этого перечисленные действия остались бы
  эксклюзивом атакующего.
- Все 38 правил переписаны на атрибуты. Правил из одного условия по `action`
  не осталось; покрытие ATT&CK сохранено — 33 из 46 техник.

**Чем проверяется.** `tests/test_leakage.py` считает взаимную информацию каждого
наблюдаемого признака с меткой и требует, чтобы ни одно значение не встречалось
только у атаки.

Тонкость, которую пришлось учесть: выборочная оценка взаимной информации
**смещена вверх** тем сильнее, чем больше у признака различных значений. Имя
ветки с тысячами уникальных значений показывало «59% информации о метке» даже
там, где связи нет. Поправка сделана перестановками: метки перемешиваются
несколько раз, средняя MI на перемешанных данных — это уровень шума для данной
кардинальности, и значимой считается только надбавка над ним.

Тест сразу нашёл ещё четыре утечки, о которых никто не подозревал:

| Признак | Снимал неопределённости | Причина |
|---|---|---|
| `actor_session` | **100%** | идентификатор сессии, общий и уникальный для шагов кампании |
| `repo` | 26% | поле проставлялось через `events.tag` только в аномальных сценариях |
| `gitlab_ok` | 39% | телеметрия обращения к API стенда, а не свойство события |
| `actor` / `role` / `project` | 21–35% | фон использовал свой список людей и репозиториев, а атакующий — из конфига |

Итог: `action` даёт 6.4% информации о метке при нуле значений-детерминаторов —
это нормальный слабый признак, а не метка.

## 2. Правило `mass-file-delete` было сломано

**Было.** Условие `{"action": "file_delete"}`. По журналу:

| действие | норма | атака |
|---|---|---|
| `file_delete` | 96 | **0** |
| `mass_delete` | 0 | 3 |

То есть правило срабатывало на каждой обычной уборке репозитория (96 ложных
тревог, ни одной верной — треть всего потока алертов) и при этом **не ловило
саму атаку**, которая эмитила другое действие. Техника T1485 числилась покрытой,
но не детектировалась — цифра покрытия была завышена.

**Стало.** Добавлен слой обогащения `detector.Enricher`: скользящие оконные
агрегаты по актору (всплески удалений, интенсивность API-чтений, охват
репозиториев). Массовость теперь **вычисляется**: 8+ удалений одним актором за
10 минут. Порог 8, а не 5, потому что команда тоже иногда чистит пачку
устаревших правил — это честный сложный отрицательный пример, и он специально
оставлен в генераторе нагрузки.

Регрессия закреплена тестом: одиночное удаление и уборка на 3 файла не дают
тревоги, 8 удалений за минуты — дают, 8 удалений за неделю — нет.

## 4. Вырожденный фон завышал качество ML

**Было.** Генератор нормального фона в `experiments.py` и `verify_ml.py`:

```python
path = rnd.choice(["rules/win/a.yml", "config/.env.example", "src/util.py", "docs/n.md"])
extra = {"shannon_entropy": 3.2 if ph else 2.4, "bytes": 200}
```

Четыре фиксированных пути и **два значения энтропии**. Норма вырождена в две
точки, атака — в другую область, классификатор разделяет их тривиально.
Отсюда рапорт «44/44 эпизодов, FP 0.0%» — артефакт генератора, а не свойство
модели. Показательно, что на единственном семействе с честным benign-двойником
(hex64 против git SHA-40) recall был 0%.

**Стало.** `research/workload.py` — один генератор на все эксперименты:

- энтропия из нормального распределения, **своя для каждого типа файла**
  (yml / py / md / json / lock / min.js / svg), с тяжёлым хвостом у
  минифицированного JS и base64-иконок;
- логнормальные размеры, benign-двойники секретов (SHA-40, UUID, base64-иконки,
  lock-файлы с хэшами, `.env.example` с плейсхолдером);
- **рабочие сессии**: люди работают очередями, а не по одному событию в час.
  Без этого «всплеск активности» отличал бы атаку тривиально — не потому, что
  атака бурная, а потому, что фон был искусственно ровным.

Честные цифры оказались заметно скромнее прежних ста процентов, и это
правильный результат.

## 5. UEBA: вероятностная модель вместо зашитых весов

**Было.**

```python
risk += 0.3   # новый репозиторий
risk += 0.2   # нетипичный час
risk += 0.2   # нетипичное действие
risk += 0.15  # всплеск
THRESHOLD = 0.45
```

Веса и порог взяты из головы, шкала ничего не означает.

**Стало.** Скор события — суммарная **неожиданность в битах**:

```
S(e) = −log₂P(repo|actor) − log₂P(action|actor)
       − log₂P(hour|actor) − log₂P(всплеск не меньше наблюдаемого)
```

| Компонента | Как оценивается |
|---|---|
| репозиторий, действие | мультиномиальное распределение со сглаживанием Дирихле: новое значение получает тем большую неожиданность, чем длиннее история актора (прежний бинарный флаг одинаково реагировал на новичка с 12 событиями и ветерана с 4000) |
| час активности | круговой KDE с ядром фон Мизеса: час — циклическая величина, 23:00 и 01:00 соседи, а обычная гистограмма считает полночь разрывом |
| всплеск | хвостовая вероятность Пуассона относительно личной интенсивности актора (EWMA) |

Слагаемые — биты информации, они сопоставимы и складываются корректно.
Порог не константа, а **квантиль эмпирического распределения под заданный
бюджет тревог**: «не более X% событий доходит до очереди» — величина, осмысленная
для SOC и напрямую управляющая нагрузкой аналитика. До накопления статистики
слой **молчит**: на первых сотнях событий профили пусты, неожиданность высока у
всех, и фиксированный порог давал лавину ложных тревог именно там, где данных
меньше всего.

Результат: точность слоя выросла с 6% до 56%.

## 6. Слияние рисков: noisy-OR при зависимых источниках

**Было.** `risk = 1 − Π(1 − rᵢ)`. Noisy-OR корректен только при условной
независимости сигналов, а правило, UEBA и ML смотрят на одно и то же событие и
срабатывают по коррелирующим причинам. Два сигнала по 0.6 давали 0.84.

**Стало.** Режим `logodds`: сумма лог-шансов с затуханием γ^i — явная поправка
на зависимость. Согласие слоёв по-прежнему повышает уверенность, но уже не
мультипликативно. Побочное полезное свойство: сигнал ровно 0.5 (неинформативный)
не добавляет ничего, тогда как noisy-OR всё равно поднимал риск.

## 7. ML доказывался отдельно и в системе не использовался

**Было.** `content_ml_features`, `train_model`, `LogReg` не встречались нигде за
пределами `research/`. Боевой детектор работал на правилах и UEBA. Работа
доказывала «ML обобщает лучше регулярок», после чего продакшн работал на
регулярках.

**Стало.** Слой **L2** встроен в `DetectionEngine`:

- `ml_features.py` — единый вектор признаков для обучения и инференса, так что
  классическое расхождение train/serve исключено конструктивно;
- `research/train_runtime_model.py` — обучение с хронологическим сплитом,
  подбором порога под бюджет ложных срабатываний и **калибровкой Платта**
  (без неё выход модели нельзя складывать с рисками других слоёв);
- признаки при обучении считаются через тот же `detector.Enricher`, что и в бою;
- модель линейная не от бедности: вклад каждого признака виден, и алерт можно
  объяснить аналитику — для SOC это важнее лишней доли AUC;
- без файла модели слой молча выключается, стенд работает на L0 + L1.

В ablation слой ML даёт precision 83% при FP 0.57% — заметно точнее правил.

## 8. Статистики не было вообще

**Было.** Все числа — точечные оценки из одного прогона с `SEED=42`.

**Стало.** `stats.py`:

| Инструмент | Зачем |
|---|---|
| интервал Уилсона | recall 41/55 — это 61–85%, а не «74.5%». Нормальное приближение при таких n и у границ 0/1 врёт |
| bootstrap | интервалы для MTTD и AUC, где аналитической формулы нет |
| **PR-AUC** | главная метрика при дисбалансе. При доле атак ~1% ROC-AUC выглядит прекрасно даже у слабого детектора |
| тест Макнемара | значимость различия двух конфигураций на **одних и тех же** эпизодах |
| поправка Холма | контроль групповой ошибки при множественных сравнениях |
| калибровочная кривая, ECE, Brier | насколько заявленная вероятность соответствует наблюдаемой частоте |

Аппарат покрыт собственными тестами (`tests/test_stats.py`): ошибка в формуле
интервала обесценила бы все выводы разом. Тест, кстати, сразу нашёл ошибку в
первой реализации PR-AUC — трапецеидальное интегрирование давало 0 на идеальном
разделителе со связками; заменено на среднюю точность с групповой обработкой
одинаковых скоров.

В `metrics.py` все доли теперь выводятся с интервалами, добавлены PR-AUC с
базовым уровнем и ROC-AUC рядом — чтобы разрыв между ними был виден.

## 9. Точность детектирования

**Было.** Precision 18.5% по событиям, 7% по инцидентам — 13 ложных тревог на
одну настоящую.

**Стало.** Появился инструмент `tools/rule_quality.py`: точность каждого правила
в отдельности, вклад в общий шум и число эпизодов, которые правило ловит
**в одиночку** (если ноль — правило можно удалить без потери recall).

По его показаниям сделано три вещи:

1. **Найдена ошибка измерения.** Оценка не применяла подавление дублей, которое
   есть в боевом конвейере: одна уборка на 12 файлов считалась как 8 отдельных
   ложных тревог, хотя аналитик увидел бы одну. Шум был завышен втрое.
2. **Подняты пороги** у правил разведки (`recon-enumeration`, `perm-discovery`,
   `code-search`) — на прежних значениях в них укладывался человек, листающий
   дерево репозитория.
3. **`ci-pipeline-change` переведён в информационные** (severity low, risk 0.3):
   правка CI происходит постоянно, и держать её как high — значит гарантировать
   поток ложных тревог. Правило осталось для контекста, но само по себе
   действенный инцидент не создаёт.

Поток тревог сократился с 963 до 295 при сохранении recall.

Честный остаток: правила разведки по-прежнему дают 5–9% точности, потому что
нормальный человек и харвестер отличаются только объёмом, а распределения
перекрываются. Это результат, а не недоделка: **правила, основанные на одном
лишь объёме, в этом контуре малопригодны поодиночке и работают только в связке
с корреляцией.**

оставался зелёным, но 31 проверка доступности и 18 проверок перевода не

и после установки обе проверки проходят по-настоящему.

## 14. Словарь перевода отстал от правил

После переписывания правил **36 из 38 названий** остались без английского
варианта: в английской версии интерфейса каталог правил был по-русски. Заметить
это можно было только глазами.

Плюс в словаре нашлось **13 дублирующихся ключей** — в JavaScript второй молча
затирает первый, и два перевода отличались по смыслу («Дежурный (on-call)» →
«On call» против «On call (on-call)»).

Появился `tests/test_i18n_rules.py`: у каждого правила обязан быть перевод, в
словаре нет дублей, нет мёртвых записей и в него не попали данные (логины,
техники ATT&CK). А `tests/test_i18n.js` теперь берёт названия **из самих
правил**, а не из зашитого списка — разойтись снова они не смогут.

## 15. Четыре правила не срабатывали ни разу

`tests/test_rule_coverage.py` связывает три вещи, которые лежали в разных
файлах и никем не сопоставлялись: что мы **умеем** ловить, что мы **реально**
исполняем и что мы **фактически** ловим.

Он сразу показал, что четыре правила молчат на всём корпусе — техника описана, а
шага атаки, который бы её исполнял, в кампаниях не существовало. Добавлены три
кампании и два примитива; теперь срабатывают все 38 из 38.

Отдельно нашлась настоящая дыра: **`comment_mr` не считал признаки содержимого**.
Секрет, вставленный в обсуждение merge request, был для детектора невидим — поля
`n_regex_hits` в событии просто не было, и правило под него не могло сработать
физически. Комментарий — такой же канал утечки, как коммит, и настоящий сканер
проверяет его наравне с кодом.

## 16. Включение слоя ML СНИЖАЛО полноту

В ablation `rules+ml` ловил 63% эпизодов против 89% у `rules` — чего не может
быть в принципе: алерты слоёв объединяются, добавление слоя не может ухудшать
обнаружение.

Причина: подавление дублей проверяло только **самый рисковый** алерт события.
Сработка ML часто оказывалась верхней по риску, попадала в окно подавления — и
утаскивала с собой сработку правила, которая дублем не была.

Теперь подавление поалертное: событие доходит до аналитика, если уцелел хотя бы
один алерт. После исправления таблица стала монотонной и осмысленной:

| слои | recall | precision | FP на норме |
|---|---|---|---|
| rules | 87.7% [76.8–93.9] | 27.7% | 3.72% |
| ueba | 12.3% [6.1–23.2] | 50.0% | 0.19% |
| ml | 49.1% [36.6–61.7] | 93.3% | 0.05% |
| **rules+ml** | **93.0% [83.3–97.2]** | **34.3%** | 3.77% |

Под уклонением `stealthy` правила падают до 70.2%, а `rules+ml` удерживает
78.9% — эшелонированная защита показана на числах, а не постулирована.

## 17. Обфускация пряталась ровно там, где правило слепло

Правило T1027 опиралось на энтропию — и исключало файлы, где высокая энтропия
ожидаема (`.min.js`, lock-файлы). Атакующий кладёт полезную нагрузку **именно
в минифицированный JS**, потому что там она и должна теряться. В результате
техника числилась покрытой и не детектировалась.

Добавлен структурный признак `obfuscation_signal`: исполнение закодированной
строки — `eval(atob(...))`, `new Function(atob(...))`, `exec(b64decode(...))`,
`| base64 -d | sh`. Отличает вредонос не «случайность» текста, а конструкция.
Обычный минифицированный JS и просто `atob(icon)` под него не подпадают.

## 18. Скрытая утечка через отсутствие поля

После добавления новых признаков содержимого тест на утечку снова покраснел:
у атакующих пушей появилось `generated_signal=False`, а у нормального фона поля
**не было вовсе** — и «поле присутствует» безошибочно указывало на атаку.

Заодно выяснилось, что `n_regex_hits >= 1` встречалось только у атаки. Значит,
правило `secret-signature-commit` имело точность 100% **по построению**, а не по
заслугам. В реальности regex регулярно срабатывает на примерах в документации,
тестовых фикстурах и отозванных ключах в changelog — теперь это есть и в фоне.

## 19. Обучение модели было неуправляемым и медленным

Сила регуляризации назначалась вручную. При слабой (3e-4) один редкий, но
идеально разделяющий признак получал вес **+18** и подминал модель под себя:
она переставала смотреть на остальные 54 признака, порог уезжал вверх, эпизодный
recall падал втрое. При сильной (2e-2) модель недообучалась.

Теперь штраф **подбирается по PR-AUC на валидации**, а обучение векторизовано
через numpy (с сохранением чистого Python как запасного пути) — перебор по сетке
занимает секунды вместо минут.

Отдельно обнаружилось, что кампании раскладывались по дням по индексу, и
хронологический сплит train/val/test оказывался **разделением по типу атаки**:
модель училась на одних кампаниях, а проверялась на других, никогда не виденных.
Задача интересная, но она должна ставиться явно, а не получаться случайно из
порядка словаря. Порядок кампаний теперь перемешивается сидом.

Итоговые цифры слоя L2: PR-AUC 0.642 при базе 0.03, ROC-AUC 0.936,
эпизодный recall 72% [59–81%], Brier 0.014.

## 20. Панель среды никогда не подгружала данные

Симптом: интерфейс открывается и выглядит нормально, но **все значения —
прочерки**, лента событий пуста, статус «stopped». В логе сервера при этом
чисто: страница и статика отдаются с кодом 200.

Причина — одна строка в разметке панели среды:

```js
innerHTML = '... <span title="merge request'ы">MR ...'
```

Апостроф внутри строки, ограниченной одинарными кавычками, закрывает её раньше
времени. Скрипт целиком не разбирался, `setInterval` не заводились, и браузер
**не делал ни одного запроса к `/api/*`**. Именно поэтому в логе не было ничего
подозрительного: там просто нечему было появиться.

Дефект прожил в проекте с самого начала — он есть в исходном коммите `9b812fb`,
до всех правок. Ни коды ответов, ни логи сервера, ни смоук-тест маршрутов его
не ловят: страница-то отдаётся исправно.

Закрыт тестом `tests/test_page_scripts.py`, который проверяет не отдачу
страницы, а её **жизнеспособность**:

1. каждый инлайновый `<script>` и каждый `static/*.js` разбирается как
   JavaScript;
2. страница доживает до конца выполнения без исключений;
3. заводятся таймеры опроса и происходит обращение к API.

Третий пункт — главный: он отличает «код синтаксически верен» от «код
работает». После исправления панель среды заводит 8 таймеров и делает 7
запросов к API при загрузке (`/api/config`, `/api/status`, `/api/health`,
`/api/repos`, `/api/insights`, `/api/events`, `/api/logs`).

Отдельно стоит отметить, что в логе пользователя выглядело подозрительным:
повторяющиеся `GET / -> 302` каждые три секунды. Это не ошибка — так панель
(`launcher.py:305`) проверяет, жив ли сайт. Проверка ходит без сессии, поэтому
её редиректит на логин; на работу это не влияет.

# Третья волна: проверка на живом стенде

Всё предыдущее измерялось на синтетическом генераторе. Проверка на реально
работающем стенде (26 384 события, 122 атаки) показала, что там детектор ведёт
себя совсем иначе: **93% инцидентов ложные, и все до одного приходят от слоя
ML**. Разбор занял большую часть этой итерации и вскрыл пять связанных дефектов.

## 21. Окно всплеска было ограничено только снизу

Главная причина. `detector.Enricher` считал агрегаты по условию `ts >= lo`, без
верхней границы. Пока поток упорядочен по времени, это работает. Но он не
упорядочен:

- красная команда датирует шаги кампании **задним числом** — «атака развернулась
  к текущему моменту»;
- журнал копится между запусками, а каждый запуск начинает симулированное время
  заново.

В живом журнале назад по времени идёт **19 565 событий из 26 292**. Для события
со «старой» меткой в окно попадала вся последующая история актора, и всплеск
раздувался с реальных 25 событий до 512 — предела очереди.

`burst_any` — самый весомый признак модели, поэтому она срабатывала почти на
каждом событии. Отсюда и «все инциденты поведенческие».

Окно стало двусторонним, плюс история актора сбрасывается на границе прогонов.
После правки максимум всплеска вернулся к 25.

## 22. Модель училась не на том распределении

Классическое расхождение train/serve: обучение шло на синтетическом генераторе,
а работать модели приходилось на живом мире с другой расстановкой событий во
времени.

Добавлен источник `--source live`: обучение по журналу стенда, с разбиением на
сегменты по границам прогонов. Веса стали осмысленными — `token_scope_api`,
`token_no_expiry`, `is_night`, `proj_secrets` вместо `burst_any`.

## 23. Бюджет тревог был задан не в том масштабе

Порог слоя L2 подбирался под «не более 1% ложных на норме». При доле атак 0.46%
это 120 ложных тревог против 7 атакующих событий — приличной точности не
получится ни при каком качестве модели.

- бюджет L2: 1% → **0.05%**;
- бюджет UEBA: 0.4% → **0.1%**;
- `ML_RISK_CAP`: 0.8 → **0.55**. Одна лишь модель больше не создаёт действенный
  инцидент: она повышает приоритет, когда СОГЛАСНА с правилом или поведением, и
  тогда слияние лог-шансов выводит риск за порог. Это и есть эшелонированная
  защита — слой добавляет уверенности, а не тревог.

## 24. Детектор ловил рабочий продукт собственной команды

Самая «жизненная» находка. Правило про учётные данные реестра контейнеров
срабатывало на файле

    rules/persistence/registry_run_key_modification.yml

а правило про пересылку почты — на

    hunts/202607_mailbox-forwarding-rule-eql.md

Формально в пути есть нужное слово. По сути это правило детектирования и
гипотеза для охоты, которые ОПИСЫВАЮТ технику и потому набиты её приметами.
Известная беда репозиториев detection engineering: они полны строк, на которые
реагируют сканеры.

Добавлен признак `security_content`; 11 правил, опирающихся на ключевые слова в
пути, исключают рабочий продукт аналитика. Ещё 16 ложных давал
`assets/icon_b64.txt` — base64-иконка; расширен `generated_signal`.

Тонкость: маска `*_b64` намеренно НЕ используется — под неё попадает выгрузка
самой атаки `export/dump_b64.txt`. Решает каталог, а не имя файла.

## 25. Новый признак обнулил детектирование на всей истории

Условие `security_content: false` не выполнялось для событий, записанных до
появления признака: поля нет, `None != False`. Выглядело как внезапно
исчезнувшая техника.

Две правки:

- признаки, выводимые **из пути**, детектор считает сам — путь есть в каждом
  событии, и полагаться на источник незачем;
- отсутствующий булев атрибут трактуется как ложь.

## Прочее в этой итерации

**Ротация логов на Windows.** Мир и защита писали в один `logs/debug.jsonl`. На
Windows файл, открытый одним процессом, нельзя переименовать из другого, поэтому
при достижении 10 МБ ротация падала — и падала на КАЖДОЙ записи, заливая консоль
трейсбеками. Теперь у каждого процесса свой файл: `debug-console.jsonl`,
`debug-webapp.jsonl`.

**Подсветка выбранного инцидента.** Клик открывал карточку сбоку, но в списке
ничего не менялось. Теперь выбранный элемент помечен тремя независимыми
признаками — цветом рамки, фоном и полосой слева, — чтобы состояние читалось и
при цветовой слепоте. Подсветка переживает автообновление списка (он
перерисовывается каждые 2.5 с), работает с клавиатуры и помечена `aria-current`.

**Проверка сквозного пути.** Кампания, запущенная из Red Launcher, прошла весь
маршрут: мир исполнил шаги → GitLab принял коммиты (359 успешных вызовов,
версия 19.0.1) → журнал → детектор → корреляция. Инцидент собрался с верной
цепочкой ATT&CK: T1098.001 → T1552.001 → T1213 → T1078, риск 0.96, помечен как
кампания.
