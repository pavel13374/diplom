## 1. Суть работы (коротко)

> **Можно ли поймать злоумышленника внутри процесса разработки, видя только
> обычный аудит-лог GitLab — коммиты, MR, CI, токены — и не имея никакой
> разметки о том, где атака?**

Чтобы это проверить, построен замкнутый стенд из двух половин, связанных
только общим журналом событий:

- **среда** генерирует правдоподобный поток жизни SOC-отдела (агенты пишут код,
  ревьюят, дежурят), в который red-team вплетает многошаговые ATT&CK-кампании;
- **защита** читает тот же поток, из которого физически вырезана разметка, и
  восстанавливает картину сама: правила → UEBA → корреляция в инциденты →
  ATT&CK → триаж.

Научная ценность работы — не в детекторе, а в **методологии честной оценки**:
разделение «мир / журнал / защита», анти-лик как исполняемый тест, и знаменатель
покрытия ATT&CK, взятый по модели угроз, а не по написанным правилам.

**Формулировка на защиту (одно предложение):**
*«Стенд, воспроизводящий поток событий SecDevOps-контура вместе с многошаговыми
атаками, и построенная на нём методика воспроизводимой оценки многослойного
обнаружения (правила + поведенческая аналитика + корреляция) в условиях
отсутствия разметки».*

## 4. Критические дефекты (P0 — чинить до защиты)

### 4.1. Правило `mass-file-delete` перепутало действие — 0% точности и 0% полноты

`detections/mass-file-delete.json`:

```json
{ "id": "mass-file-delete", "technique": "T1485", "when": { "action": "file_delete" } }
```

Факт по журналу:

| действие | benign | атака |
|---|---|---|
| `file_delete` | **96** | **0** |
| `mass_delete` | **0** | **3** |

`file_delete` эмитит только `agents/base.py:118` — обычный сотрудник.
Атака (`_a_mass_deletion`) эмитит `mass_delete`, и его **не ловит ни одно правило**.

Последствия — тройные:

1. Правило даёт **96 алертов, все ложные** — это 35% всего потока алертов и
   главный вкладчик в FP-rate 93%.
2. Техника **T1485 (Data Destruction) фактически не детектируется**, хотя
   числится покрытой → цифра покрытия 71.7% завышена.
3. В названии правила написано «массовое удаление», а условия на массовость нет
   вообще — ни окна, ни порога, ни счётчика. Это одиночное событие.

**Фикс:** `when: {"action": "mass_delete"}` + отдельное правило на всплеск
`file_delete` (≥N за окно) через корреляцию, а не через одиночное событие.

## 5. Методологические дыры (самое опасное на защите)

### 5.1. ⚠️ Анти-лик пробит через словарь действий

Это главная находка ревью.

`test_antileak.py` проверяет, что из события вырезаны `is_anomaly`,
`episode_id`, `technique_id` и прочие метки. Проверка честная и работает.
**Но поле `action` само является меткой** для целого класса событий:

| действие | benign | атака |
|---|---|---|
| `token_create` | 0 | 8 |
| `mass_delete` | 0 | 3 |
| `repo_enum` | 0 | 2 |
| `steal_oauth`, `perm_discovery`, `exfil_altproto`, `obfuscated_payload`, `history_rewrite`, `deploy_tool_abuse`, `automated_collection` | 0 | по 1 |

Десять типов действий встречаются **исключительно** у атакующего. А **19 из 38
правил состоят ровно из одного условия** вида `{"action": "steal_oauth"}`.

Такое правило — не детектор, а тавтология: оно читает метку, просто под другим
именем. Формально анти-лик пройден, фактически — нет.

Вопрос комиссии, на который сейчас нет ответа: *«Ваш детектор ловит `repo_enum`.
А откуда в реальном аудит-логе GitLab возьмётся событие с типом `repo_enum`?»*
В настоящем логе есть только `GET /api/v4/projects` — обычный запрос, который
нужно **вывести** из частоты и последовательности, а не прочитать готовым.

**Как чинить (и превратить в главу работы):**

1. Ввести нормализацию: мир эмитит *низкоуровневые наблюдаемые* действия
   (`api_call`, `push`, `member_update`), а «разведка», «кража токена» —
   это то, что детектор должен **вывести** из признаков.
2. Добавить в `test_antileak.py` проверку: *никакое значение никакого
   наблюдаемого поля не должно иметь взаимной информации с меткой выше порога*.
   Это ~30 строк кода и очень сильный аргумент на защите.
3. Пересчитать метрики после — они честно упадут, и это **правильный** результат
   для диплома. Падение метрик с объяснением причины ценится выше, чем красивые
   цифры без него.

либо мир должен соблюдать политику ревью, либо правило должно учитывать
контекст (защищённая ветка, критичный репо, отсутствие апрува *и* критичный

вердиктам», но реальную precision нигде не показывает.
**Комиссия найдёт это за 5 минут — лучше рассказать самому и с объяснением.**

### 5.4. Синтетический фон вырожден — отсюда «идеальные» ML-цифры

`verify_ml.py` рапортует **44/44 эпизода (100%) при FP 0.0%**, а

Смотрим, как сделан benign-фон (`tools/verify_ml.py:80`, `research/experiments.py:98`):

```python
path = rnd.choice(["rules/win/a.yml", "config/.env.example", "src/util.py", "docs/n.md"])
extra={"shannon_entropy": 3.2 if ph else 2.4, ...,  "bytes": 200}
```

Четыре фиксированных пути и **два фиксированных значения энтропии**. Норма

**Фикс:** benign-фон с распределениями (энтропия ~ N(μ,σ) по типам файлов,

## 6. Чего не хватает: математика

Сейчас математики в проекте почти нет — это самый заметный пробел для диплома.

### 6.1. UEBA — набор зашитых констант, а не статистика

`detector.py`, класс `UEBA`:

```python
risk += 0.3   # новый репозиторий
risk += 0.2   # нетипичный час
risk += 0.2   # нетипичное действие
risk += 0.15  # всплеск
THRESHOLD = 0.45
```

Веса взяты из головы, порог тоже. Нет ни распределения, ни оценки параметров,
ни калибровки. Это эвристика, и её нельзя защищать как «поведенческую
аналитику».

**Что поставить вместо (по возрастанию сложности):**

| Сигнал | Сейчас | Как надо |
|---|---|---|
| нетипичный час | `hours[h] <= 1` | круговая статистика: von Mises по часу активности, аномалия = логплотность ниже квантиля |
| новый репозиторий | флаг «раньше не было» | Dirichlet-мультиномиальный prior над репозиториями актора → `-log P(repo \| actor)`, естественно учитывает объём истории |
| всплеск активности | счётчик > 14 | Poisson/negative-binomial на интенсивность + CUSUM или EWMA-контрольная карта |
| нетипичное действие | флаг | та же мультиномиальная модель, `surprisal = -log p` |
| итоговый скор | сумма констант | сумма surprisal'ов = **логарифм совместной вероятности**; порог из хвоста эмпирического распределения |

Эта замена даёт то, чего сейчас нет: **скор в интерпретируемых единицах
(биты неожиданности)** и порог, выведенный из данных, а не назначенный.

### 6.2. `fuse()` — noisy-OR при заведомо зависимых источниках

```python
risk = 1 - Π(1 - r_i)
```

Noisy-OR корректен **только при условной независимости** сигналов. Здесь
правило и UEBA срабатывают на одном и том же событии по коррелированным
причинам — независимости нет, и риск систематически завышается: два сигнала по
0.6 дают 0.84.

Плюс более базовая проблема: `risk` в правилах (0.4…0.95) — **не вероятность**,
а экспертное число, но формула обращается с ним как с вероятностью.

**Что сделать:**
- калибровка: Platt scaling или isotonic regression, чтобы `risk` стал реальной
  P(атака | сработка) — считается по имеющимся вердиктам TP/FP;
- либо честная логистическая комбинация: `logit(p) = Σ wᵢ·xᵢ`, веса обучены на
  размеченных эпизодах — тогда зависимость учтена;
- показать в работе **калибровочную кривую** (reliability diagram) до и после.
  Это ровно та математика, которую хотят видеть.

### 6.3. Нет ни одной кривой качества для боевого детектора

ROC есть только для игрушечной контент-модели (`experiments_roc.py`).
Для основного детектора (правила+UEBA) нет ни ROC, ни PR-кривой, ни AUC.

При precision 18.5% и сильном дисбалансе классов (104 аномальных события из
25 973 → 0.4%) **ROC вводит в заблуждение — нужен Precision-Recall и PR-AUC**.
Это отдельный, вполне «дипломный» тезис: объяснить, почему при дисбалансе
1:250 ROC-AUC выглядит прекрасно, а система непригодна.

### 6.4. Отсутствующие статистические процедуры

Для работы такого объёма ожидается, и сейчас нет ничего из списка:

- **доверительные интервалы** на recall/precision — Wilson score interval,
  10 строк кода, сразу видно, что 74.5% на 55 эпизодах это 61–85%;
- **bootstrap** (1000 ресэмплов) для интервалов на MTTD и AUC;
- **тест значимости** различий конфигураций — McNemar на парных исходах
  (rules_only vs full на одних и тех же эпизодах) — то, что нужно для
  ablation-таблицы;
- **множественные прогоны** с разными сидами (≥10) + разброс;
- **поправка на множественные сравнения** (Holm/BH), если сравнений много;
- **анализ чувствительности**: как метрики зависят от `UEBA_THRESHOLD`,
  `window_min` корреляции, `ALERT_SUPPRESS_MIN` — сейчас это магические числа
  в `config.py` без обоснования;
- **кривая обучения** — сколько дней фона нужно UEBA, чтобы стабилизироваться
  (сейчас `MIN_EVENTS = 12`, взято с потолка);
- **экономическая метрика** — стоимость FP × alert fatigue против стоимости
  пропуска; при 93% FP это единственный способ честно оценить систему.

### 6.5. Корреляция — эвристика на одном признаке

`Correlator` склеивает алерты по `(actor, окно 180 минут)`. Ограничения:

- один открытый инцидент на актора — параллельные кампании сольются в одну;
- нет связи по репозиторию, по MR, по цепочке артефактов;
- `is_campaign` = «≥2 разных тактик» — без учёта порядка и осмысленности
  перехода между тактиками;
- `_stable_iid` = `sha1 % 90000000`; при коллизии делается `iid += 1`, что
  **ломает само свойство стабильности**, ради которого хэш и вводился.

**Что предложить:** граф сущностей (actor–repo–MR–artifact) и связывание по
компонентам связности; либо марковская модель переходов между тактиками
ATT&CK — тогда «цепочка похожа на kill-chain» становится вероятностью, а не
подсчётом. Это хорошая тема для отдельного раздела.

## 8. Что хорошо (не потерять при доработке)

Честно: этого много, и это выше типового уровня.

1. **Архитектурное разделение мир/журнал/защита** — методологически грамотно и
   правильно подано в записке.
2. **Анти-лик как исполняемый тест** — сама идея сильная (пробой в §5.1 не
   отменяет ценности подхода, а даёт материал для главы).
3. **Знаменатель покрытия ATT&CK по модели угроз**, а не по своим правилам, с
   явным объяснением «иначе метрика мерит сама себя» — это зрелое рассуждение,
   его надо озвучить на защите отдельно.
4. **Detection-as-Code** — правила в JSON, декларативные, редактируются без
   перезапуска логики. Правильная индустриальная практика.
5. **Комментарии объясняют «почему», а не «что»** — в `metrics.py` прямо
   написана история: «раньше FP считался по всем детектам и полз к 75%». Это
   редкость и это ценно.
6. **Graceful degradation везде**: нет sklearn → свой логрег; нет Ollama →
   детерминированный фолбэк; нет jsdom → SKIP, а не FAIL; нет GitLab → offline.
7. **Доступность и i18n как тесты** (WCAG-контраст, роли, клавиатура, RU/EN) —
   этого не делает почти никто.
8. **Стабильные ID инцидентов** ради переживания рестарта вердиктами —
   продуманная деталь.
9. **Реальный мониторинг GitLab** (`gitlab_watch.py`) — «поймай меня сам»
   работает по наблюдаемым признакам. Сильный демонстрационный ход.
10. **Leave-one-family-out holdout** — методологически правильный дизайн
    эксперимента (претензия только к вырожденности генератора).

## 12. Резюме одним абзацем

Работа большая, живая и с правильно поставленным вопросом — методология
«мир / журнал / защита» и честный знаменатель ATT&CK-покрытия сами по себе
тянут на диплом. Ломает её измерительная часть: одно перепутанное правило даёт
треть всех алертов и роняет точность до 7%, глава экспериментов не запускается
из-за однострочного бага, ML доказан отдельно и в систему не встроен, а
анти-лик — главная методологическая гордость проекта — пробит через словарь
имён действий. Математики в текущем виде почти нет: UEBA это пять зашитых
констант, слияние рисков — noisy-OR на заведомо зависимых источниках, ни одного
доверительного интервала на весь проект. Всё перечисленное чинится за 4–5 дней,
причём **каждый из этих дефектов при исправлении превращается в содержательный
раздел работы** — что для диплома даже выгоднее, чем если бы их не было.
