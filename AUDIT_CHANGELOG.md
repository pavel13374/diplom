## FIX-1 · T1562 Impair Defenses: правила не могли сработать никогда

**Файлы:** `gitlab_client.py`, `agents/base.py`, `webapp.py`, `tests/test_offline.py`
**Компонент:** мир → событие `mr_merge` → правила `merge-without-approval`, `self-merged-mr`

**Проблема.**
`agents/base.merge_mr` брал число апрувов из объекта merge request:
`_mr.get("approvals_count")`, с запасным вариантом `len(_mr.get("approved_by"))`.
В GitLab API объект MR **не содержит ни того, ни другого** — они живут в
отдельной ручке `/projects/:id/merge_requests/:iid/approvals`. Поэтому `_ac`
всегда был `None`, и поле `approvals_count` не попадало ни в одно событие.

Проверено на журнале: из **6 013** событий `mr_merge` поле присутствует в **0**.
Соседние поля из того же блока (`self_merged`, `protected_branch`, `mr_author`)
проставлены в 98–100% событий, то есть `get_mr` работает — не приходят именно
апрувы. В свежих событиях (2026-08-29, `gitlab_ok: true`) картина та же.

Следствие: оба правила, закрывающие технику **T1562**, содержат условие
`approvals_count == 0`, которое не может выполниться. Техника числилась
покрытой на экране ATT&CK, но не детектировалась. Приёмочный прогон это
подтвердил независимо: 30 красных кампаний, из них 8 шагов с техникой T1562
(`weaken_protection`, `merge_without_review`) — **0 срабатываний**.

**Изменение.**
1. `gitlab_client.py` — добавлен метод `get_mr_approvals(project_id, mr_iid)`,
   читающий `/merge_requests/:iid/approvals`. Возвращает `int` либо `None`,
   если GitLab недоступен или в ответе нет нужных полей.
2. `agents/base.py::merge_mr` — если объект MR апрувов не дал, число берётся
   из новой ручки. Поле пишется для ВСЕХ merge-событий, как и раньше
   (анти-лик: наличие поля не должно быть подсказкой детектору).
3. `webapp.py` — в `_FAKE_UNANNOTATED` добавлен контракт `get_mr_approvals: None`.
   Это принципиально: аннотация `Optional[int]` сама по себе дала бы
   int-заглушку (1), и offline-прогон подделывал бы «ревью было» на каждом
   merge. `None` означает «неизвестно», и поле в событие просто не пишется.
4. `tests/test_offline.py` — см. FIX-4.

**Почему так, а не «понизить порог».** Здесь нечего понижать: поля не было
вовсе. Число апрувов — наблюдаемая величина из аудит-лога GitLab, её нельзя
ни выдумать, ни вывести; её надо запросить.

**Проверка.**
- Разбор ответов ручки на 6 формах ответа (есть `approvals_count`; только
  `approved_by`; пустой ответ; мусор) — 6/6 как ожидалось, при недоступном
  GitLab возвращается `None`.
- Детектор на синтетических событиях:
  `approvals_count=0` + protected + self_merged → срабатывают
  `merge-without-approval`, `self-merged-mr`, техника **T1562**;
  `approvals_count=2` → тишина (ложных срабатываний не добавилось);
  поле отсутствует → тишина (сегодняшнее поведение воспроизведено).
- `run_tests.py`: 21/21 PASS.

**НЕ ПРОВЕРЕНО вживую.** Мир — работающий процесс Python на Windows; он
исполняет код, загруженный при старте. Чтобы правка попала в поток событий,
нужен перезапуск (`STOP.bat` → `START.bat`), выполнить который из среды
аудита нельзя. После перезапуска ожидается: поле `approvals_count`
появляется в событиях `mr_merge`, кампания `review_bypass_push` даёт
срабатывание T1562, «покрыто» и «срабатывало» на экране ATT&CK сходятся.

## FIX-2 · T1087 Account/Repo Discovery: сценарий тише порога правила

**Файл:** `activities/anomaly.py` (`_a_recon_enumeration`)
**Компонент:** сценарий разведки → `api_read` → правило `recon-enumeration`

**Проблема.**
Сценарий выдавал РОВНО 5 событий `api_read`. Правило требует
`burst_api_read_15m >= 8` и `api_items_sum_15m >= 300`. Пороги были подняты
с 5/150 до 8/300 по замеру точности (см. `rationale` и `tuning_note` в
`detections/recon-enumeration.json`: на прежних порогах правило давало 14%
всего шума, потому что человек, листающий дерево репозитория, в них
укладывался). Объём сценария при этом не подняли.

Проверено прогоном 6 000 свежих событий через детектор (ровно один вызов
`process()` на событие): максимальный всплеск на путях `/projects` и
`/repository/tree` равен **5** при пороге 8 → **0 срабатываний**.
Приёмочный прогон подтвердил: техника T1087 исполнена 6 раз (шаги
`recon_enumeration` в трёх кампаниях) — **0 срабатываний**.

**Изменение.** Сценарий теперь выдаёт обход дерева по каждому из 5
репозиториев постранично: 1 запрос `/projects` + 2–3 страницы
`/repository/tree` на репозиторий = 11–16 запросов.

**Почему чинился мир, а не правило.** Порог получен измерением на нормальном
трафике; понизить его — вернуть 14% шума и подделать покрытие. Неверна была
модель атаки: настоящий перебор репозиториев в аудит-логе GitLab — это
десятки запросов, а не пять. Нижняя граница выбрана так, чтобы всплеск был
выше порога ВСЕГДА (`randint(2,3)`, а не `randint(1,3)`): иначе техника
считалась бы покрытой через раз.

**Проверка.**
- Синтетический прогон нового объёма (14 запросов) через детектор:
  `recon-enumeration` срабатывает, техника **T1087**, тактика Reconnaissance,
  риск 0.55.
- `run_tests.py`: 21/21 PASS (включая `rule-coverage`, который проверяет,
  что правила не молчат на корпусе).

**НЕ ПРОВЕРЕНО вживую** — по той же причине, что и FIX-1: нужен перезапуск мира.

## FIX-4 · Проверка offline-контракта запрещала единственный честный ответ

**Файл:** `tests/test_offline.py`

**Проблема.** Проверка соответствия заглушки аннотации сравнивала значение с
РАСКРЫТЫМ типом: для метода с `Optional[int]` она требовала `int` и
браковала `None`. Между тем для `get_mr_approvals` (FIX-1) `None` —
единственный честный ответ в offline: числа апрувов там не существует, а
int-заглушка означала бы «ревью было» на каждом merge, то есть подделанные
апрувы в каждом offline-прогоне.

**Изменение.** `None` принимается, если ИСХОДНАЯ аннотация — `Optional[...]`.
Проверка осталась строгой: не-`None` значение неверного типа по-прежнему провал.

**Проверка.** `tests/test_offline.py` — PASS; полный прогон 21/21 PASS.
Проверка продолжает ловить исходный дефект: метод без аннотации и без записи
в `_FAKE_UNANNOTATED` по-прежнему валит тест (именно так она поймала FIX-1 на
полпути).

## FIX-7 · Токен Telegram уходил в журнал целиком

**Файл:** `telegram.py` (переписан)

**Проблема — доказана исполнением.** `telegram.py` логировал отказ так:
`logger.warning(f"telegram send failed: {e}")`. Библиотека `requests` кладёт в

применяется в консольном форматтере, в JSON-форматтере, в кольцевом буфере

## FIX-9 · У консоли защиты не было консольного вывода вообще

**Файлы:** `soclog.py`, `console_app/__init__.py`, `webapp.py`

**Проблема.** `soclog.install()` поднимает JSON-файл, `errors.log` и кольцевой
буфер — и ни одного `StreamHandler`. Процесс защиты не писал в stdout ничего,
кроме баннера и строк доступа werkzeug. Именно он крутит детектор, коррелятор
и триаж — и наблюдать за ним было нечем. У мира вывод был, но своим,
третьим по счёту форматом (`%H:%M:%S I name: msg`): без даты, без имени
сервиса, без структурного контекста. `simulator.log` не содержал даже
`%(name)s` — по строке нельзя было понять, какая подсистема её написала.

**Изменение.** Единый формат для всех процессов и всех приёмников:

```
2026-08-30 00:31:12.345 INFO     defense  correlator         инцидент открыт  incident_id=84674023 actor=anna.smirnova alerts=6 risk=0.99
└─ время с мс ────────┘ └уровень┘ └сервис┘ └─ компонент ───┘ └─ событие ──┘  └─ контекст: важные идентификаторы впереди ─┘
```

- `soclog.install_console()` — stdout, цвет только в терминале (в трубу не
  льём: панель раскрашивает сама);
- `soclog.install_file()` — `logs/app-<сервис>.log`, тот же формат, ротация;
- `soclog.SERVICE` — имя сервиса (`world` / `defense` / `metrics`), выводится
  в каждой строке и в JSON;
- контекст (`incident_id`, `rule_id`, `actor`, `technique`, …) теперь виден
  В КОНСОЛИ, а не только в `debug-*.jsonl`; важные идентификаторы печатаются
  первыми, пустые значения опускаются;
- фильтр строк доступа: 4xx/5xx видны всегда, успешный опрос своего API — по
  `SOC_LOG_ACCESS=all` (иначе он занимает 90% журнала).

## FIX-15 · START_PANEL.bat не разбирался cmd.exe

**Файл:** `START_PANEL.bat` (плюс CRLF во всех остальных `.bat`)

**Проблема — моя собственная, найдена вами на живой машине.** Я записал батник
в UTF-8 с кириллицей в комментариях и с переводами строк в стиле Unix.
`cmd.exe` читает `.bat` в кодировке OEM (cp866 на русской Windows) ПОБАЙТНО:
многобайтные последовательности UTF-8 распадаются, часть байтов приходится на
служебные символы `&`, `|`, `(`, `)`, строка рвётся, и cmd пытается выполнить
обломки как команды:

```
'ся' is not recognized as an internal or external command
'from' is not recognized as an internal or external command
'Сервисы' is not recognized as an internal or external command
```

`chcp 65001` внутри файла не спасает: комментарии выше него уже прочитаны в
старой кодировке. Одиночные LF вдобавок ломают многострочные блоки
`if errorlevel 1 ( ... )`.

Показательно, ЧТО именно сломалось: `'Сервисы'` — это хвостовой `echo` ПОСЛЕ
запуска панели. То есть панель всё это время запускалась нормально, а мусор
сыпался при выходе. Диагноз по одному тексту ошибки был неполным.

**Изменение.** `START_PANEL.bat` переписан в чистом ASCII с CRLF (0 не-ASCII
байт, 55 CRLF, 0 одиночных LF); весь текст для человека — в `panel.py`, где
Python печатает его под UTF-8. Остальные семь `.bat` в корне переведены на
CRLF без изменения содержимого — у всех была та же латентная проблема.

**Проверка.** Новый тест `test_bat_files_are_cmd_safe()` в
`tests/test_generated_content.py`: ASCII в `START_PANEL.bat` и CRLF во всех
батниках. Плюс подтверждение с живой машины — запуск 2026-08-30 01:10 прошёл
через панель (`===== запуск ... (panel) =====` в обоих журналах).
