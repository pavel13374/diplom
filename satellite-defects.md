## 1. Транспорт сателлит↔центр не восстанавливается после обрыва

**Это главный дефект.** Он стоил 470 миллионов событий.

### Как устроено

Сателлит и центр связаны leafnode-соединением NATS. На стороне центра его держит компонент `nats-bridge`. По этому каналу вниз едут конфигурации, справочники и активные списки, наверх — собранные события.

### Что происходит

Под нагрузкой сервер не успевает отдать данные в канал за отведённый таймаут и разрывает соединение. Затем **цикл переподключения умирает окончательно** — попытки прекращаются навсегда, до ручного перезапуска пода.

### Доказательства

Случай первый, 29.07:

```
15:53:49  Slow Consumer (Write Deadline)
15:54:11  переподключился
15:54:52  снова Slow Consumer
15:55:04  переподключился
15:55:25  снова Slow Consumer
15:55:33  переподключился
16:01:34  Leafnode Error 'Stale Connection' → Client Closed
          ← после этого в логе НИ ОДНОЙ попытки переподключения
```

Восстановлено вручную 30.07 в 07:15. **Простой 15 часов 22 минуты.**

Случай второй, 30.07:

```
13:45:38  Slow Consumer Detected: WriteDeadline of 10s exceeded
          with 1 chunks of 1569706 total bytes
13:45:38  Slow Consumer Recovered
13:49:18  Leafnode Error 'Stale Connection' → Client Closed
          ← снова тишина
```

Восстановлено вручную в 15:50. **Простой 2 часа.**

### Сеть при этом была исправна

Проверено прямым подключением к порту с мастера во время простоя:

```
timeout 5 bash -c 'cat < /dev/tcp/satellite-kb-01.ussc-soc.ru/30072'
→ INFO {"server_id":"NBLOG...","domain":"space-satellite-rvsiem",...}
→ OPEN
```

Сателлит отвечал своим баннером. Связь можно было восстановить в любую секунду — но никто этого не делал, потому что bridge перестал пытаться, а мониторинг молчал.

### Что требуется

Устойчивый цикл переподключения с экспоненциальной задержкой и без условий, при которых он прекращается навсегда.

## 2. Буфер транспортного стрима рассчитан на 10–20 секунд

Именно поэтому обрыв превратился в безвозвратную потерю, а не в отложенную доставку.

### Расчёт

Стрим `r-space-broadcast-commands-input`, через который едут события с сателлита:

```
max_bytes:  104 857 600 (100 MiB)
discard:    old
поток:      800–2000 сообщений/с × ~5,8 КБ = 5–11 МБ/с
```

Замер окна хранения на main:

```
first_ts  2026-07-30T07:15:12
last_ts   2026-07-30T07:15:21
          ← девять секунд
```

### Следствие

Любой сетевой сбой длиннее ~20 секунд гарантированно приводит к потере данных. Хуже того, зеркало после такого разрыва **не может догнать источник** — нужных ему сообщений там уже нет.

Подтверждение после первого инцидента:

```
main:      first_seq 2 479 909 647
сателлит:  last_seq  2 479 317 751
           ← пропуск ~590 000 сообщений
```

Зеркало навсегда осталось в состоянии `Retrying mirror consumer` и в итоге было снесено реконсайлером.

### Потери

Проверка по ClickHouse за период первого инцидента:

```
2026-07-29 12:00   30 437 546
2026-07-29 13:00   30 614 606
2026-07-29 14:00   30 788 505
2026-07-29 15:00   18 203 998   ← обрыв в 15:53
2026-07-29 16:00 … 2026-07-30 06:00   ПУСТО
2026-07-30 07:00      989 998   ← восстановление
```

При базовой скорости 30,6 млн событий в час потеряно **примерно 470 миллионов событий**.

### Что требуется

Либо `max_bytes` на порядки больше (сутки автономности при 5 МБ/с — это около 430 ГБ), либо возрастной лимит `max_age` вместо байтового, либо отдельный стрим под события с адекватным буфером.

## 3. `data_sync` паникует при таймауте

### Что происходит

```
thread 'vector-worker' panicked at src/data_sync.rs:60:22:
Failed to create Object Store:
  Error { kind: BucketCreate, source: Some(Error { kind: TimedOut, source: None }) }
```

Компонент синхронизации конфигурации не дождался ответа JetStream API и **упал в панику вместо повтора попытки**.

### Почему это плохо

Паника убила рабочий поток, но процесс продолжил работать. Через два часа после события:

```
restarts=0    STATUS: Running    READY: 2/2
```

Kubernetes видит здоровый под. Liveness-проба проходит. Vector принимает syslog. А синхронизация конфигурации при этом мертва — за 15 минут наблюдения ни одной строки `file-sync`.

Это худший вид отказа: система выглядит исправной и не подаёт признаков проблемы. Обнаружить можно только вычитывая логи вручную.

### Что требуется

Повтор попытки с задержкой вместо паники. Как минимум — отражение состояния в readiness-пробе, чтобы отказ был заметен.

## 4. Лимиты бакетов не применяются к зеркалам сателлитов

### Что произошло

По инструкции вендора лимиты бакетов активных списков подняты со 100 MiB до 1 GiB. Инструкция покрывает два домена: `main` и space-инстанс основного кластера.

Зеркало `KV_r-space-active-lists` на сателлите имеет **собственный** лимит и в инструкции не упомянуто. Результат сразу после восстановления связи:

```
KV_r-space-active-lists   Mirror   Active 535ms   Lag 3 649
```

Связь есть, зеркало живое, а лаг стоит — источник вырос за 100 MiB, зеркало принять больше не может.

### Дополнительно по инструкции

Два расхождения с документом вендора:

- Домен space-инстанса — `space-main-rvsiem`, а в инструкции указан `space-main-evo`. Шаг 8.2 падает с `no responders available`.
- Перезапуск `space-manager` новые лимиты к существующим бакетам не применяет. Параметры из ConfigMap действуют только при создании. Вендор предполагает одну ручную правку, фактически потребовалось три, плюс две на сателлите.

## 5. RTT до сателлита 622 мс, компрессия выключена

### Измерение

Из `leafz` на `nats-bridge-0`:

```
nats-space-0  rtt 4,49 мс     ← локальный, основной кластер
nats-main-0   rtt 3,09 мс     ← локальный
nats-space-0  rtt 621,79 мс   ← сателлит КБ
```

### Почему это объясняет Slow Consumer

При RTT 0,62 с и потребности 5 МБ/с произведение полосы на задержку составляет около **3 МБ данных в полёте одновременно**. Стандартные TCP-окна столько не удерживают — отправитель упирается в неподтверждённые данные и останавливается.

Отсюда и запись в логе: «полтора мегабайта не удалось отдать за десять секунд», то есть эффективная скорость упала ниже 150 КБ/с.

### Компрессия не используется

```
"compression": "s2_uncompressed"
```

События передаются в сыром виде. Это protobuf с текстовыми полями — S2 ужимает такое втрое-вчетверо. Включение `s2_auto` на leafnode-ремоуте снизило бы нагрузку на канал в разы **и это единственная мера, которая уменьшает трафик, а не повышает терпимость к перегрузке**.

### Что требуется

Включить компрессию. Отдельно выяснить природу задержки: если в спокойном состоянии RTT десятки миллисекунд, значит 622 мс были следствием перегрузки; если сотни — канал такой по природе, и параметры транспорта надо подбирать под него.

## 6. Часы виртуальной машины опережали реальные на 5 часов

### Что было

```
Local time:   19:29:58 +05
Universal:    14:29:58 UTC
Time zone:    Asia/Yekaterinburg (+05)
System clock synchronized: no
```

Настоящий UTC в этот момент — 09:30. Часовой пояс выставлен верно, врали сами часы.

### Причина

ВМ работает на QEMU/KVM (`pc-i440fx-10.0`, SeaBIOS в дебиановской сборке). Судя по симптому, в конфигурации задано хранение RTC в местном времени: гость получает при старте 14:29 и трактует это как UTC, затем прибавляет свои +05 и показывает 19:29.

### Как исправлено

Синхронизация через `ptp_kvm` — часы берутся напрямую с гипервизора, без внешнего NTP:

```
modprobe ptp_kvm
refclock PHC /dev/ptp0 poll 2 dpoll -2 offset 0
```

### Осталось

Настройку ВМ должны поправить виртуализаторы (`<clock offset='utc'/>` или `qm set --localtime 0`), иначе при каждой перезагрузке будет повторяться, пока chrony не догонит.

Заодно там же стоит исправить топологию CPU — сейчас гость видит `sockets=1, cores=1, threads=8`, то есть одно ядро с восемью потоками, чего не бывает на реальном железе. Должно быть `cores=8, threads=1`.

### Побочный эффект

Сертификаты k0s, перевыпущенные при сбитых часах, получили `notBefore` на пять часов в будущем. Управление кластером было недоступно до 18:25, работали через `--insecure-skip-tls-verify`. Восстановилось само.

## 7. Время событий syslog сдвинуто на 5 часов

### Симптом

События писались в ClickHouse, но не отображались ни в графиках EPS, ни в поиске за последние минуты.

```
нормализованное событие   last_seen 2026-07-30 14:22:04
корреляционное событие    last_seen 2026-07-30 09:22:21   ← верное UTC
```

14,8 млн событий за восемь часов ложились на пять часов вперёд.

### Причина

Проверено перехватом трафика на порту 30514:

```
<14>Jul 30 14:28:37 repa033 audisp-syslog: type=SYSCALL msg=audit(1785403717.713:247033): ...
```

Это формат RFC 3164 — **без года и без часового пояса**. Хосты пишут местное екатеринбургское время. Vector обязан чем-то дополнить зону, берёт UTC из окружения контейнера и получает сдвиг ровно на пять часов.

Сверка по эпохе из самой audit-записи подтверждает:

```
audit(1785403717...)  =  09:28:37 UTC  =  14:28:37 по Екатеринбургу
```

### Как чинить

Три варианта, от лучшего:

1. **Брать время из `msg=audit(EPOCH)`** — величина абсолютная, не зависит ни от зоны хоста, ни от настроек коллектора. Правится в одном месте, работает для всех 450 хостов.
2. **Указать часовой пояс на точке входа** — `timezone = "Asia/Yekaterinburg"`. Быстро, но применится ко всем источникам этой точки входа.
3. **Перевести rsyslog на RFC 5424** — тогда в заголовке появится смещение `+05:00`. Правильно архитектурно, но требует раскатки на все хосты.

## 8. Дубликаты доставки syslog

Одно и то же событие приходит дважды, отличаясь только наличием поля `procid`:

```
Row 890: …"hostname":"veeam039",…"severity":"info","timestamp":"…"}
Row 891: …"hostname":"veeam039",…"procid":542425,"severity":"info","timestamp":"…"}
```

Похоже на два маршрута доставки в rsyslog — RFC 3164 и RFC 5424 одновременно, либо два правила `omfwd`. Требует проверки конфигурации на источниках.

Для дедупликации в запросах пригоден `audit_id` вида `audit(<epoch>:<serial>)` — он уникален.

## 9. Отсутствие мониторинга связности

Это не дефект продукта, а наш пробел, и он превратил первый инцидент из десятиминутного в пятнадцатичасовой.

Пятнадцать с половиной часов система не собирала события с целой площадки. Ни одного оповещения не сработало. Обнаружено случайно, при разборе постороннего вопроса.

Два признака, каждый из которых поймал бы оба инцидента за минуты:

**Число leafnode-соединений на bridge.** Норма — три. Упало до двух → тревога.

```bash
curl -s localhost:8222/leafz | python3 -c "import json,sys; print(json.load(sys.stdin)['leafnodes'])"
```

**Возраст зеркал.** В норме сотни миллисекунд, при обрыве — часы. Самый однозначный индикатор.

```bash
nats --context rspace-nats stream report
# колонка Active в блоке Replication Report
```

Плюс проверка сверху: если в ClickHouse за пять минут меньше ста тысяч событий — что-то не так.

## Что делать дальше

**Немедленно, силами эксплуатации:**

Поднять мониторинг числа leafnode-соединений и возраста зеркал. Это ничего не меняет в конфигурации и окупилось бы уже дважды за одни сутки.

Исправить время событий syslog — предпочтительно через использование epoch из `audit(...)` в правиле нормализации.

**Через виртуализаторов:**

Настройка RTC ВМ в UTC вместо местного времени. Топология CPU `cores=8, threads=1`. Заодно, при остановке ВМ, добавление ядер — сейчас коллектор упирается в лимит и троттлится.

**В обращение к вендору:**

Дефект переподключения `nats-bridge` — два воспроизведения за сутки с полными логами.

Объём буфера транспортного стрима — 20 секунд автономности на канале между площадками нежизнеспособны.

Паника `data_sync` при таймауте вместо повтора, с молчаливой потерей функциональности.

Компрессия leafnode — при RTT 622 мс и потоке 5 МБ/с её отсутствие является прямой причиной `Slow Consumer`.

Инструкция по расширению бакетов — не учитывает домены сателлитов, содержит неверный домен `space-main-evo` и неполный список ручных правок.
